# 지도 위의 한 점을 맞추는 동안, 팀의 좌표도 맞춰갔다

레벨 3에서 내가 가장 많이 배운 것은 기능 구현과 협업이 별개의 일이 아니라는 점이다. 맡은 일을 끝까지 이해하고 검증해야 팀에 설명할 수 있었고, 그 근거가 있어야 내 의견도 꺼낼 수 있었다. 그렇게 서로의 생각과 작업의 맥락을 공유하며 팀의 좌표를 맞춰갔다.

내가 레벨 3에서 표현하고 싶은 말을 한 문장으로 정리하면 이렇다.

> 맡은 일을 끝까지 이해하고 검증한 뒤, 그 근거로 의견을 꺼내 팀과 같은 방향을 바라보는 법을 배웠다.

## 내 아이디어를 내려놓고 새로운 팀에 합류하기

레벨 3의 시작은 병원 진료 준비 서비스였다. 병원에 가기 전에 증상과 질문을 정리할 수 있는 서비스를 만들고, 사용자에게 프로토타입을 보여주며 반응을 확인했다.

처음에는 좋은 아이디어와 기능을 만들면 사용자가 필요성을 느낄 것이라고 생각했다. 하지만 인터뷰를 해보니 내가 생각한 문제와 사용자가 실제로 겪는 문제에는 차이가 있었다. 질문도 바꿔야 했고, 내가 생각한 타깃 사용자도 다시 정의해야 했다.

이후에는 이 아이디어를 팀 프로젝트로 계속 이어갈지 고민했다. 의료 도메인은 더 깊이 이해해야 할 부분이 많았고, 내가 원하는 사용자를 지속적으로 만나 검증하기도 쉽지 않았다. 결국 내 아이디어를 끝까지 지키는 것보다, 이번 레벨에서 실제 사용자와 만나며 서비스를 만들어가는 경험이 더 중요하다고 판단했다.

그렇게 내 아이디어를 내려놓고 Mapmory 팀에 합류했다. 처음에는 내가 만든 아이디어를 내려놓는 것이 아쉽기도 했다. 하지만 좋은 개발자는 자신이 만든 것을 끝까지 고집하는 사람이 아니라, 더 나은 문제와 방향을 선택할 수 있는 사람일 수도 있다고 생각하게 되었다.

Mapmory는 여행 사진과 기억을 장소 중심으로 기록하는 서비스였다. 나도 여행 후 사진첩을 보며 “이 사진을 어디에서 찍었지?”라고 생각한 적이 많았기 때문에, 직접 사용할 것 같은 서비스라는 점이 마음에 들었다.

돌이켜보면 내 아이디어를 내려놓은 것은 단순히 프로젝트를 바꾼 일이 아니었다. 문제를 바라보는 기준을 혼자 정하는 대신, 새로운 팀과 함께 만들어보기로 한 첫 번째 선택이었다.

## 맡은 일을 화면 밖까지 설명하기

팀에 합류한 뒤에는 내가 맡은 기능을 구현하는 것만큼, 왜 그런 방향을 선택했는지 설명하는 일이 중요했다.

Mapmory 팀은 Android 개발자 2명과 Backend 개발자 3명으로 구성되었다. 처음에는 MVP 범위, API, 도메인, 배포 방식, 지도 구현 방법처럼 정해야 할 것이 많았다.

외부 지도 SDK를 사용하지 않고 GeoJSON을 이용해 지도를 직접 그리기로 했을 때도 처음부터 모든 원리를 알고 있었던 것은 아니다. 처음에는 AI가 만들어준 코드와 설명을 참고해 기능을 빠르게 구현했다.

하지만 어느 순간부터 “이 코드가 왜 이렇게 동작하지?”라는 질문이 계속 생겼다. GeoJSON의 Polygon이 어떻게 Compose Canvas의 경로가 되는지, 화면의 클릭 좌표가 어떻게 위도·경도로 바뀌는지, 그 좌표가 어떻게 지역 코드로 연결되는지 제대로 이해해야 했다.

Mapmory를 테스트하던 중 지도에서 부산광역시 금정구를 눌렀다. 지도에는 분명 금정구라고 표시되어 있었는데, 기록 작성 화면으로 이동하자 부산광역시 중구가 나타났다. 서울특별시 서초구처럼 아예 아무 반응이 없는 지역도 있었다.

처음에는 단순히 지도 경계가 잘못 그려졌거나 클릭 영역이 어긋난 문제라고 생각했다. 하지만 코드를 따라가 보니 문제는 더 깊은 곳에 있었다. 지도에 표시되는 지역명, 지도 경계가 가진 코드, 앱의 `Location`이 사용하는 코드가 서로 다른 기준을 가지고 있었다.

예를 들어 GeoJSON의 평창군 코드는 `32340`이었지만, 앱에서 사용하는 평창군의 코드는 `51760`이었다. 일부 시·도 코드는 수동으로 변환하고 있었지만 시·군·구 코드는 제대로 변환되지 않고 있었다.

지도에서 금정구를 눌렀을 때 중구가 나타난 것은 특정 지역의 오타가 아니었다. 서로 다른 기준의 데이터가 연결되는 과정에서 생긴 문제였다.

한 지역만 예외 처리하면 빠르게 해결할 수 있을 것 같았다. 하지만 그렇게 하면 다른 지역에서 같은 문제가 반복될 수 있었다. 그래서 이 문제를 단순한 클릭 버그가 아니라 지도와 기록 화면 사이의 데이터 계약 문제로 봐야 한다고 생각했다.

지도에 표시되는 모든 Polygon이 앱과 서버가 함께 사용하는 `regionCode`를 가져야 한다고 정리했다. 원본 GeoJSON을 앱 실행 중에 매번 가져오는 대신, 개발·빌드 단계에서 코드를 앱의 기준에 맞게 변환하고 정적인 지도 데이터로 포함하는 방향을 제안했다.

이후에는 지도에 보이는 지역명과 기록 작성 화면에 전달되는 지역명을 하나씩 비교했다. 평창군을 누르면 `51760`으로 해석되는지, 강남구를 누르면 `11680`으로 연결되는지 확인했다. 하나의 사례만 고친 것이 아니라 모든 지역이 같은 기준으로 연결되는지를 테스트하려고 했다.

사진 추천 기능을 구현할 때도 비슷한 고민을 했다. 처음에는 Room에 사진을 저장한다고 하면 사진 원본을 저장하는 것처럼 생각했다. 하지만 실제로는 MediaStore에서 사진 목록을 가져오고, Room에는 사진의 URI·수정 시각·GPS 좌표 같은 메타데이터만 저장했다.

캐시에 없는 사진이나 변경된 사진만 EXIF GPS를 다시 읽도록 하여 불필요한 작업을 줄였다. 테스트 기기에서는 위치 기반 사진 추천 전체 시간이 약 300ms에서 174ms로, 메타데이터 동기화 시간이 81ms에서 37ms로 줄어드는 것을 확인했다.

다만 이것이 모든 기기에서 같은 결과를 보장한다는 뜻은 아니었다. 특정 기기에서 측정한 개선 결과와 일반적인 성능 보장은 구분해야 했다.

AI가 작성한 코드를 그대로 사용하지 않기 위해 나만의 기준도 만들었다.

- 이 코드가 어떤 입력을 받는지 설명할 수 있는가?
- 성공·실패·취소 상황을 구분할 수 있는가?
- 문제가 생겼을 때 어느 계층을 확인해야 하는지 알고 있는가?
- 작은 단위의 테스트나 로그로 동작을 검증할 수 있는가?

설명할 수 없으면 구현이 끝난 것이 아니라고 생각하려고 했다. 이 기준은 혼자 잘하기 위한 규칙이라기보다, 내가 맡은 일을 팀에 설명할 수 있게 만드는 최소한의 기준이었다.

이 경험을 통해 내가 맡은 일을 해낸다는 것은 화면 하나를 완성하는 것과 다르다는 것을 알게 되었다. 내가 만든 기능이 어떤 데이터를 사용하고, 그 데이터가 다음 화면에서 어떤 의미로 해석되는지까지 설명할 수 있어야 했다.

## 혼자 빠르게 끝내는 방식의 한계

하지만 맡은 일을 이해하고 해내는 것만으로는 충분하지 않았다. 내가 알고 있는 맥락을 팀원과 공유하지 않으면 팀의 좌표는 맞춰지지 않았다.

프로젝트 초반에는 각자 맡은 파트를 잘 완성하면 팀도 자연스럽게 잘 굴러갈 것이라고 생각했다. Android는 Android대로, Backend는 Backend대로 작업하고 PR을 올리면 된다고 생각했다.

하지만 시간이 지나면서 문제가 드러났다. 서로의 작업 상황을 충분히 알지 못했고, Android 작업과 Backend 작업이 하나의 PR에 섞이는 경우도 있었다. 어떤 브랜치가 최신인지, 이미 병합된 코드인지, 아직 적용되지 않은 코드인지 확인하는 데에도 시간이 들었다.

나는 작업을 빨리 끝내는 데 집중한 나머지 다른 팀원이 내 작업의 맥락을 이해하는 데 필요한 설명을 충분히 남기지 못한 적도 있었다. 반대로 다른 팀원의 코드를 리뷰할 때도 작성 의도를 알기 어려워 코드 자체를 처음부터 추측해야 했다.

결국 우리 팀은 프로젝트가 지나치게 개인화되어 있다는 문제를 꺼내놓았다. 겉으로는 큰 갈등이 없었지만, 각자가 자신의 작업을 따로 처리하는 방식으로 흘러가고 있었다.

그 이후부터는 어제 한 일과 오늘 할 일을 간단히 공유하기 시작했다. 작업 중인 이유와 막힌 지점을 문서와 PR에 남기려고 했다.

이 변화는 거창한 도구를 도입해서 생긴 것이 아니었다. 서로의 현재 상태를 알 수 있도록 작은 정보를 꾸준히 공유한 결과였다.

이 과정을 통해 문서화는 나중에 보고서를 작성하기 위한 기록이 아니라, 팀원이 같은 상황을 바라보기 위한 장치라는 것을 배웠다.

## 의견을 말하고 함께 검증하기

팀의 상황을 공유하기 시작하면서, 의견을 말하는 방식도 다시 생각하게 되었다.

우리 팀의 그라운드 룰 중 하나는 “모든 의견에 좋다고 하지 말고, 필요하면 반박하기”였다.

처음에는 이 규칙이 좋은 서비스를 만들기 위해 필요하다고 생각하면서도, 실제로 반박하는 일은 조심스러웠다. 내가 충분히 알고 있지 않은 것 같거나, 괜히 분위기를 어렵게 만드는 것은 아닐까 하는 생각이 들었다.

앞서 말한 지도 문제를 특정 지역의 예외 처리로 끝내면 빠르게 보일 수는 있었다. 하지만 결국 같은 문제가 다른 지역에서 반복될 가능성이 높았다.

그래서 이 문제를 이야기할 때는 “한 지역의 버그를 고치자”가 아니라, “지도 데이터와 앱 데이터의 기준을 통일해야 한다”라고 말할 수 있어야 했다.

의견은 크게 말한다고 설득되는 것이 아니었다. 문제를 재현할 수 있어야 했고, 왜 문제가 생겼는지 설명할 수 있어야 했고, 어떤 방식으로 확인할지까지 제안할 수 있어야 했다.

내가 생각한 방향이 항상 정답이었던 것도 아니다. 팀원들의 의견을 듣고 범위를 줄이거나 방법을 바꾼 경우도 많았다.

중요한 것은 내 의견을 끝까지 관철하는 것이 아니었다. 더 나은 결론을 만들기 위해 의견을 꺼내고, 팀원들과 함께 검증하는 과정이었다.

이제는 의견을 말하지 않는 것이 갈등을 피하는 방법이 아니라, 팀이 판단할 근거를 잃게 할 수도 있다는 것을 안다. 동시에 의견을 냈다는 이유만으로 내 방향을 고집해서도 안 된다는 것도 배웠다.

## 레벨 3를 마치며

레벨 3를 시작할 때 나는 기능을 구현하는 Android 개발자가 되는 것을 가장 많이 생각했다. 하지만 지금 돌아보면 가장 크게 배운 것은 기능 구현 자체보다 제품과 팀을 함께 바라보는 방법이었다.

사용자에게 프로토타입을 보여주고 예상과 다른 반응을 확인했다. 내 아이디어를 내려놓고 새로운 팀에 합류했다. Mapmory를 실제 사용자에게 배포했고, 기능이 동작하는 것과 사용자가 자연스럽게 사용하는 것이 다르다는 것도 알게 되었다.

기술적으로는 지도 경계 데이터와 서버 데이터를 어떤 기준으로 연결할지 고민했고, 사진 메타데이터 캐시와 테스트를 통해 성능을 측정했다. AI가 작성한 코드를 그대로 받아들이지 않고, 내가 설명하고 검증할 수 있는 코드로 바꾸려고 했다.

협업에서는 혼자 빠르게 작업하는 것보다 서로의 상황을 공유하며 같은 방향을 바라보는 것이 중요하다는 것을 배웠다. 우리 팀은 완벽하게 매끄러운 팀은 아니었지만, 어긋난 부분을 그냥 넘기지 않고 대화를 통해 다시 맞춰가려고 했다.

레벨 3가 끝난 뒤에도 Mapmory를 계속 개선하고 싶다. 하지만 다음에는 기능을 더 많이 만드는 것만 목표로 삼고 싶지는 않다. 사용자가 실제로 어디에서 불편을 느끼는지 확인하고, 그 근거를 팀과 공유하고, 결정한 일을 끝까지 검증하는 개발자가 되고 싶다.

지도 위의 지역 하나를 정확하게 연결하려면 여러 데이터의 좌표가 같아야 한다. 팀도 비슷했다. 서로 다른 생각을 가진 사람들이 같은 목표와 맥락을 공유할 때 비로소 앞으로 나아갈 수 있었다.

레벨 3에서 내가 남긴 것은 코드만이 아니었다. 문제를 의심하고, 맡은 일을 설명하고, 의견을 말하고, 사람들과 다시 좌표를 맞춰본 경험이었다.
