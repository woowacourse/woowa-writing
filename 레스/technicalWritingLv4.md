# E2E가 714개가 된 뒤

## 10월 23일 저녁

10월 23일 저녁 6시 46분, 채팅 기능을 지운 PR이 dev에 머지되었습니다. 채팅 테스트도 같이 빠져서 E2E가 9분 30초 만에 끝났어요. 그 주 들어 처음으로 CI가 짧아졌습니다.

4분 뒤에는 그룹별 즐겨찾기 PR이 머지되었습니다. 브라우저 하나에 140개였던 E2E가 233개로 늘었고 다음 dev push에서는 E2E만 25분 24초가 걸렸습니다. job 제한 시간이 30분이었으니 거의 끝까지 간 셈입니다.

그 전날과 그날, 이틀 동안 30분을 넘겨 취소된 job이 7개였습니다. CI를 53번 돌린 PR도 있었어요. 37번은 새로 push해서 취소되었고 16번은 실패했습니다. 그 PR 하나에 CI가 사용한 시간을 더하면 496분이었습니다. CI가 초록이 아닌 상태로 머지한 PR도 이 이틀에만 5개 나왔습니다. 그 전에는 한 번도 없던 일입니다.

실패하면 다시 돌리고 기다렸는데 기다리는 사이 다른 PR이 먼저 머지되면 충돌을 풀었고 그러면 CI가 처음부터 다시 돌았습니다. 답답했습니다. 어디가 문제인지도 모르고 기다리기만 하는 것이 가장 답답했어요.

얼마 전 이 블로그에 "코드를 빨리 만드는 만큼 그 코드를 검증하는 체계도 함께 다시 설계해야 한다"고 적은 적이 있습니다. 이번 글은 그 말대로 해 본 기록입니다. 연어 프론트엔드의 Playwright E2E가 왜 느려졌는지 먼저 재어 보고 그 숫자를 보면서 설치 단계, 브라우저, 테스트 개수를 차례로 줄였습니다.

## 30개에서 714개

연어는 출퇴근 광역버스 좌석을 예보하는 서비스입니다. 프론트엔드는 두 명이고 서로 PR을 리뷰합니다. 둘 다 AI 코딩 도구로 기능을 만들고 테스트도 같이 만듭니다.

9월 24일에 E2E를 CI에 처음 붙였습니다. 테스트는 세 브라우저를 합쳐 30개였고 62초면 끝났어요. Chrome, Firefox, Safari에서 같은 테스트를 돌렸고 워커는 하나였고 실패하면 두 번까지 다시 돌렸습니다. 서버는 webpack 개발 서버를 띄웠고 API 요청은 전부 mock으로 막았습니다.

이 설정은 한 달 동안 거의 그대로였는데 테스트는 계속 늘었습니다.

| 날짜 | 테스트 수 (브라우저 3개 합) | E2E 단계 |
|---|---|---|
| 9월 24일 | 30 | 62초 |
| 9월 30일 | 144 | 5.6분 |
| 10월 15일 | 324 | 11.7분 |
| 10월 24일 | 714 | 22.5분 |

10월 15일에는 지도와 바텀시트로 만든 판정 보드가 들어오면서 테스트가 한꺼번에 늘었습니다. 22일에는 iOS 네이티브 지도와 소셜 로그인, 23일에는 즐겨찾기 테스트가 들어왔어요. 기능을 하나 붙이면 테스트도 같이 붙었습니다.

주별로 테스트 하나에 걸린 시간을 나누어 보면 2.0초에서 2.4초였습니다. 한 달 내내 비슷했어요. 테스트가 무거워진 것이 아니라 개수가 24배가 되었을 뿐입니다.

## CI 기록 310회

무엇부터 줄일지 정하기 전에 지난 기록부터 보았습니다.

`gh run list`로 CI 실행 310회를 받았고 jobs API에 있는 단계별 시작 시각과 끝 시각으로 E2E 단계와 job 시간을 구했습니다. 로그가 남아 있는 job 176개에서는 Playwright가 마지막에 찍는 요약 줄로 테스트 수와 실패 수, 재시도로 통과한 수를 셌습니다. 실패했거나 재시도가 있었던 job 44개는 로그를 전부 받아서 실패한 테스트 이름과 첫 에러 줄을 모았습니다.

모아 보니 생각과 다른 것이 몇 가지 있었습니다.

### 실패 18번

E2E 단계에서 실패한 실행은 18번이었고 원인은 다섯 가지였습니다.

| 원인 | 실패한 실행 | 어디 문제였나 |
|---|---|---|
| mock을 해제하는 순간과 응답이 겹침 | 3 | 테스트 |
| 다른 PR이 바꾼 문구를 모르고 예전 문구를 확인 | 1 | 테스트 |
| 화면 캡처를 macOS에만 있는 경로에 저장 | 9 | 테스트 |
| 요청을 막는 코드가 이미 처리된 요청을 다시 막으려 함 | 2 | 테스트 |
| 닉네임을 저장하는 중에 화면을 떠나면 마이페이지로 되돌아감 | 6 | 제품 |

제품 버그로 실패한 것은 6번, 버그는 하나뿐이었어요. 나머지 12번은 테스트 코드나 테스트 환경을 고쳐서 해결했습니다.

캡처 경로 문제는 PR 하나에서 시작되었습니다. 그 PR 테스트가 Linux CI에는 없는 경로에 캡처를 저장하려다 실패했는데 이 코드가 dev에 머지된 뒤로는 dev를 병합한 다른 PR들도 같은 이유로 실패했습니다. 9번 중 5번이 이렇게 다른 사람 PR에서 난 실패였어요.

### 재시도로 통과한 버그

CI는 실패한 테스트를 두 번까지 다시 돌리고 다시 돌려서 통과하면 초록으로 표시합니다. 10월 19일부터 한 주 동안 재시도로 통과한 테스트가 하나라도 나온 실행이 35%였습니다.

닉네임 버그도 처음에는 실패로 보이지 않았습니다. WebKit에서 가끔 실패했다가 재시도에서 통과했어요. 그렇게 10번을 통과하는 동안 아무도 기록을 열어 보지 않았고 그 사이 이 버그가 든 버전이 운영에 배포되었습니다.

원인은 이랬습니다. 닉네임 화면은 사용자가 화면을 떠났는지를 `useEffect` cleanup으로 판단했습니다. 그런데 `BrowserRouter`는 화면 이동을 `startTransition`으로 처리합니다. 주소는 이미 바뀌었고 cleanup은 아직 돌지 않은 짧은 틈에 저장 응답이 오면, 화면은 사용자가 아직 떠나지 않았다고 보고 마이페이지로 되돌려 보냈습니다.

테스트는 처음부터 실패하고 있었는데 재시도 뒤에 뜬 초록 표시만 보고 지나쳤던 것입니다. 이게 가장 뼈아팠습니다.

### 브라우저별 결과

10월 20일 실행 하나를 브라우저별로 나누어 보면 Chromium 252초, Firefox 305초, WebKit 260초였습니다. 워커가 하나라서 이 셋을 더한 817초가 곧 E2E 단계 14분이었어요.

실패도 브라우저마다 달랐습니다. Firefox에서만 실패한 실행은 0번, WebKit에서만 실패한 실행은 7번이었고 제품 버그도 WebKit에서만 나왔습니다.

운영 기록도 보았습니다. 최근 30일 동안 판정 보드를 본 사용자의 브라우저 상위 10개를 보면 WebKit 계열이 40명, Chromium 계열이 34명이었고 Firefox는 없었습니다. iOS 앱도 WKWebView로 웹을 띄웁니다. 정리하면, 가장 느리고 사용자는 사용하지 않고 혼자 실패한 적도 없는 브라우저를 PR마다 돌리고 있었습니다.

### 리뷰 대기 시간

10월 19일 이후 머지된 PR 19개는 PR을 열고 머지하기까지 중앙값 5.5시간이 걸렸습니다. 그중 CI는 37분, 11% 정도였어요. 평소에는 CI보다 리뷰를 기다리는 시간이 훨씬 길었습니다.

그래도 CI를 줄여야 했던 이유는 두 가지입니다. job이 30분 안에 끝나야 했고 머지가 몰린 날이나 실패를 고치느라 push를 여러 번 한 PR에서는 CI 때문에 머지가 늦어졌습니다.

### 로컬과 CI

같은 변경도 어디서 재는지에 따라 결과가 달랐습니다. 워커를 2개로 늘렸을 때 제 컴퓨터(18코어)에서는 시간이 절반으로 줄었는데 CI 러너(4 vCPU)에서는 PR이 18%에서 36%, dev push가 24% 줄었습니다. 개발 서버를 운영 빌드로 바꾼 것도 로컬에서 Chromium만 돌렸을 때는 29% 줄었지만 CI와 같은 조건으로 다시 재니 13%였어요. 그래서 이후로는 CI와 같은 조건에서 잰 숫자만 비교했습니다.

숫자를 다 보고 나서, 줄이기 전에 하나를 먼저 정했습니다. 사용자 여정 테스트는 지우지 않는다는 것입니다. 닉네임 버그처럼 단위 테스트로는 재현하기 어려운 화면 이동 타이밍 문제를 잡은 것도 E2E였으니까요. 줄일 대상은 실행 방식과, 같은 흐름에서 조건만 바꾸어 반복하는 테스트로 정했습니다.

## 설치에 29분

가장 먼저 고친 곳은 E2E 앞의 설치 단계였습니다.

`Install Playwright browsers` 단계는 보통 48초면 끝났습니다. 10월 23일 실행 25번 중 21번도 1분 11초 안에 끝났어요. 그런데 3번은 18분에서 29분이 걸렸고 테스트를 하나도 못 돌린 채 30분 제한에 걸려 취소되었습니다.

로그를 보니 브라우저를 내려받는 데는 16초밖에 걸리지 않았고 오래 걸린 쪽은 `--with-deps` 옵션이 apt로 받는 시스템 패키지였어요. 119MB를 초당 109KB로 받고 있었습니다. 코드와 상관없이 미러 속도 때문에 job이 취소되고 있었던 것입니다.

캐시도 생각해 보았지만 브라우저 폴더는 캐시해도 시스템 패키지는 결국 apt로 다시 받아야 해서 미러가 느린 날에는 똑같이 느립니다.

그래서 시스템 패키지를 아예 받지 않기로 했습니다. E2E를 별도 job으로 분리하고 그 job을 Playwright 공식 컨테이너 이미지에서 돌렸습니다. 이미지 안에 브라우저와 시스템 패키지가 들어 있어서 설치 단계를 지울 수 있었습니다.

```yaml
frontend-e2e:
  needs: playwright-version
  timeout-minutes: ${{ github.event_name == 'pull_request' && 30 || 45 }}
  container:
    image: mcr.microsoft.com/playwright:v${{ needs.playwright-version.outputs.version }}-noble
```

이미지 버전은 앞에 둔 작은 job이 `pnpm-lock.yaml`에서 Playwright 버전을 읽어서 넘깁니다. 설치된 패키지 버전과 이미지 버전이 다르면 브라우저를 못 찾기 때문입니다. lint, 타입 검사, jest, 빌드는 원래 job에 그대로 두고 두 job을 동시에 시작하게 했어요. 이미지를 못 받아도 빌드 결과는 따로 확인할 수 있습니다.

단점도 있습니다. 압축해도 956MB인 이미지를 실행할 때마다 받아야 합니다. 이미지 레지스트리에 장애가 나거나, lock 파일에 적힌 Playwright 버전의 이미지가 아직 나오지 않았으면 job이 시작하자마자 실패합니다.

바꾼 뒤로 컨테이너 준비는 26초에서 44초 걸렸습니다. 11월 1일까지 E2E job 36번을 다시 보니 중앙값은 27초였고 설치 때문에 취소된 실행은 없었습니다. 평균은 몇 초 줄었고 29분 걸리던 날은 아예 사라졌어요.

## PR에서는 브라우저 두 개만

앞에서 본 숫자를 다시 꺼내 보면 Firefox에서만 실패한 실행은 0번, WebKit에서만 실패한 실행은 7번이었고 사용자 브라우저 상위 10개에 Firefox는 없었습니다.

그래서 PR에서는 Chromium과 iPhone 15만 돌리기로 했습니다. iPhone 15는 393x659 화면에 터치를 켠 WebKit입니다. Firefox와 데스크톱 Safari는 dev나 main에 push될 때만 돌리고 push job 제한 시간은 45분으로 늘렸습니다. 같은 dev 기준으로 PR E2E가 1351초에서 943초로 줄었습니다.

브라우저마다 job을 나누는 방법도 있었습니다. 세 브라우저를 그대로 돌리면서 기다리는 시간을 줄일 수 있지만 설치와 lint와 빌드를 job마다 반복하거나 빌드 결과를 job끼리 넘겨야 합니다. 테스트를 여러 job에 나누어 돌리는 샤딩은 이때 비교하지 않았고 dev push가 다시 제한 시간에 가까워지면 그때 보기로 했습니다.

대신 Firefox나 데스크톱 Safari에서만 깨지는 문제는 dev에 머지한 뒤에야 알 수 있어서 dev push에서 이런 실패가 4주에 두 번을 넘으면 그 브라우저를 PR에 다시 넣기로 했습니다. 이후 dev와 main push 16번 동안 그런 실패는 없었습니다.

같은 주에 실행 방식도 몇 가지 바꾸었어요.

| 바꾼 것 | 전 | 후 |
|---|---|---|
| CI 워커 수 (dev push) | 1개, 27.7분 | 2개, 21.0분 |
| trace에 DOM 스냅샷 기록 (로컬 Chromium) | 모든 시도, 165초 | 첫 실패 시도만, 스냅샷 없이 139초 |
| E2E 서버 | webpack 개발 서버 | 운영 빌드와 정적 서버 |

마지막 줄을 바꾸다가 생각지 못한 버그를 찾았습니다.

### 운영 빌드에서만 실패한 테스트

E2E 서버를 운영 빌드로 바꾸자 iPhone 15에서만 지도 화면 테스트 6개가 매번 실패했습니다. 개발 서버에서는 계속 통과하던 테스트였어요. 처음에는 테스트를 의심했는데 따라가 보니 문제는 화면 쪽에 있었습니다.

`index.html`은 Google 폰트 CSS를 다 받기 전까지 첫 화면을 그리지 않는 방식으로 불러오고 있었어요. WebKit에서는 이 CSS를 받는 동안 앱이 먼저 그려지면 그때 스타일을 한 번 계산하고 CSS가 도착하면 다시 계산하면서 그 차이만큼 CSS transition을 시작합니다. 판정 보드 행 높이가 260ms 동안 15px에서 76px로 커지고 글자색 두 곳이 200ms 동안 바뀌었습니다.

이 transition은 테스트에서 멈춰 둔 시계와 상관없이 실제 시간으로 움직였기 때문에 테스트는 행이 커지는 도중에 위치를 재고 그 자리를 눌렀습니다.

개발 서버에서 통과했던 이유도 알게 되었습니다. 개발 번들은 크고 느려서 앱이 그려지기 전에 폰트 CSS가 먼저 도착했지만 운영 번들은 작고 빨라서 순서가 바뀌었습니다. 모바일 데이터로 처음 들어오는 아이폰 사용자도 같은 화면을 볼 수 있었습니다.

원인을 좁히려고 후보를 하나씩 켰다 꺼 보니 번들 설정을 바꾸어도 계속 실패했고 폰트 CSS만 바로 빈 응답으로 주면 통과했으며 1.5초 늦게 주면 다시 실패했습니다.

테스트는 손대지 않았어요. 폰트 link를 `media="print"`로 불러오고 `onload`에서 바꾸도록 고쳐서 첫 화면을 막지 않게 했습니다. 이후 PR E2E 중앙값은 8.8분에서 6.5분이 되었습니다. 그래도 이때 일로 오래 기억에 남은 것은 이 버그입니다. 실행 시간을 줄이려고 서버를 바꾸었는데 덕분에 사용자가 겪을 수 있는 버그를 먼저 찾았습니다.

## 비슷한 테스트 묶기

실행 방식을 고쳐도 하루에 테스트가 90개씩 늘면 시간은 다시 늘어납니다. 마지막으로 테스트 개수를 보았습니다.

10월 20일 기준으로 브라우저 하나에 테스트가 133개 있었는데 그중 44개가 같은 흐름을 조건만 바꾸어 반복하고 있었습니다. 화면 너비, 모션 줄이기 설정, 로그인 여부, 데이터 개수 같은 조건이었어요. 하나씩 보면 다 이유가 있었지만 모아 놓고 보니 같은 화면을 같은 순서로 여러 번 확인하고 있었습니다.

조건만 다른 테스트는 대표 테스트 하나로 묶고 조건은 `test.step` 이름에 적었습니다. 실패하면 어떤 조건에서 깨졌는지 이름만 보고 알 수 있게 하려고요. 화면 없이 확인할 수 있는 것은 jest로 옮겼습니다. 픽셀, 색, 애니메이션 중간값을 확인하던 부분은 가로로 넘치는지, 가려지는지처럼 사용자가 실제로 보는 결과를 확인하도록 바꾸었습니다.

어디까지 줄이면 될지 기준을 정하는 데 가장 오래 걸렸습니다. 사용자 여정 수가 그대로인지로 판단하려면 무엇을 여정으로 볼지부터 다시 정해야 했어요. 그래서 지우는 테스트마다 그 테스트가 확인하던 내용이 대표 테스트나 jest로 옮겨졌는지 하나씩 대조했습니다. 옮길 곳이 없는 확인은 테스트를 되살리거나, 없어도 되는지 따로 판단했습니다.

브라우저 하나에 306개였던 테스트가 235개가 되었습니다. 머지 직전에 dev 변경을 합친 뒤 기준으로는 303개에서 243개입니다. jest는 756개에서 769개로 늘었습니다. 머지 직전 PR E2E는 6분에서 8분 걸렸는데 머지 직후에는 4.4분에서 4.8분이었습니다.

## healer

테스트가 이만큼 많고 코드를 AI가 만들다 보면, 실패한 테스트를 고치는 일도 AI에게 맡기게 됩니다. 그래서 Playwright Test Agents의 healer를 사용해 보았습니다. healer는 실패한 테스트를 받아서 원인을 찾고 테스트를 고치는 에이전트입니다.

먼저 제품 코드에 일부러 버그를 넣었습니다. 남은 시간 조건 `seconds <= 60`을 `seconds <= 120`으로 바꾸었어요. 기본 healer는 Claude Code와 Codex 둘 다 같은 행동을 했습니다. 버그라고 알려 주지 않고 제품 코드를 원래대로 되돌려서 테스트를 통과시켰어요. 두 도구 모두 두 번씩 그랬습니다.

테스트는 다시 초록이 되었지만 버그가 있었다는 기록은 남지 않았습니다. 재시도 뒤에 닉네임 버그가 묻혔던 것과 같은 상황이었어요.

그래서 규칙을 하나 넣었습니다. 지금 브랜치에서 제품 코드의 그 문구를 직접 바꾼 diff가 있을 때만 테스트 기대값을 고칩니다. 그렇지 않으면 테스트를 고치지 않고 근거와 함께 "제품 버그 의심"이나 "판단 못 함"으로 보고합니다. 커밋은 사람이 합니다.

규칙을 넣은 healer는 일부러 문구를 바꾼 경우에는 기대값 한 줄만 고쳤습니다. 일부러 넣은 버그, 앞에서 본 폰트 버그, 버그와 단위 테스트 기대값을 같이 바꾼 경우에는 테스트를 건드리지 않고 모두 제품 버그 의심으로 보고했습니다.

마지막 경우는 팀원이 리뷰에서 찾아 주었어요. 처음 규칙은 단위 테스트 diff도 근거로 보았기 때문에 버그에 맞춰 단위 테스트 기대값까지 바꾸면 healer가 그 diff를 의도한 변경으로 보고 E2E를 고쳐 버릴 수 있었습니다. 근거를 찾을 때 단위 테스트와 mock 파일을 빼서 막았습니다.

push하면 CI를 지켜보다가 E2E가 실패했을 때 healer 판정을 알림으로 보내 주는 hook도 만들었습니다. 다만 원하는 사람만 켜게 했습니다. healer가 각자의 사용량을 소모하고 백그라운드에서 프로세스를 띄우기 때문입니다.

## 아직 남은 것

| | 10월 24일 | 11월 1일 |
|---|---|---|
| PR E2E 단계 | 22.5분 (714개) | 6.4분 (중앙값, 18번) |
| dev push E2E 단계 | 25.0분 | 14.0분 (중앙값, 14번) |

숫자로는 끝난 것처럼 보이지만 테스트를 줄이고 이틀 뒤인 11월 1일에 보니 dev push 테스트가 951개에서 1041개로 다시 늘어 있었습니다. 브라우저 하나로 나누면 265개로, 10월 24일보다 많습니다. 기능이 붙는 속도가 그대로니 테스트도 그 속도로 늘어납니다.

재시도 문제도 그대로입니다. 10월 30일부터 11월 1일까지 성공한 실행 32번 중 17번에서 재시도로 통과한 테스트가 나왔습니다. 이 기록을 누가 언제 볼지는 아직 정하지 못했습니다. 새 E2E를 어떤 기준으로 추가할지, CI가 초록이 아닌 PR은 머지하지 못하게 막을지도 아직 정하는 중입니다.

돌아보면 가장 도움이 된 것은 고치기 전에 먼저 재어 본 일이었습니다. 실패 18번을 하나씩 열어 보기 전에는 12번이 테스트 쪽 문제였다는 것도, 하나뿐인 제품 버그가 재시도로 10번이나 통과했다는 것도 몰랐습니다.

AI로 테스트가 빠르게 늘어나는 팀에서 CI 때문에 고민하고 있다면, 고치기 전에 지난 실패를 원인별로 한 번 나누어 보시길 권합니다. 저희는 그 표를 보고 어디부터 손댈지 정했습니다.
