# 멀티 모듈 리팩토링을 진행하며

room 도메인 중심의 단일 모듈을 4개 모듈로 나눴다.

## 모듈 구조 요약

| 모듈                 | 계층(Layer)         | 주요 역할 및 포함 요소                                                                                                                                                             | 포트 / 어댑터 구분                                              |
|--------------------|-------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------|
| **core**           | Domain Layer      | 도메인 규칙·모델 정의<br>• Entity, Value Object, Domain Service, Domain Exception<br>• **Repository 인터페이스**                                                                        | **Outbound Port** (Repository)                           |
| **application**    | Application Layer | 유스케이스 오케스트레이션<br>• Service, Scheduler, Application Exception<br>• 외부 연동용 **Port 인터페이스**                                                                                   | **Inbound Port**(Use Case), **Outbound Port**(외부 호출 추상화) |
| **infrastructure** | Adapter Layer     | 기술 구현체 및 외부 연동<br>• Controller(REST/GraphQL/gRPC) = **Inbound Adapter**<br>• JPA/QueryDSL 등 Repository 구현, 외부 API(Discord 등) = **Outbound Adapter**<br>• Config/Converter | **Inbound/Outbound Adapter**                             |
| **api**            | Bootstrap Layer   | 실행·조립(Spring Boot 진입점)<br>• `@SpringBootApplication` main, 설정/환경 구성                                                                                                       | (포트/어댑터 없음)                                              |

### 의존 관계 요약

- **application -> core**  
  application 계층은 core의 도메인 모델과 규칙을 사용한다.

- **infrastructure -> core**  
  infrastructure 계층은 core의 Repository 인터페이스(Outbound Port)를 구현한다.

- **infrastructure -> application**  
  infrastructure 계층은 application이 정의한 Port(Outbound Port)를 구현하며,  
  또한 Controller를 통해 application의 Inbound Port(유스케이스)를 호출한다.

- **api -> application, infrastructure**  
  api 계층은 실행 시점에 application과 infrastructure를 조립하고,  
  스프링 컨텍스트를 초기화하는 역할을 맡는다.

---

즉, 의존성은 항상 **바깥에서 안쪽으로** 흐른다.  
core는 어떤 모듈에도 의존하지 않고,  
application은 core에만 의존하며,  
infrastructure는 core와 application을 구현하고,  
api는 나머지 모든 모듈을 실행 시점에 묶는다.

# 1. core

## Entity (POJO VS ORM-managed)

```java
package com.estime.room;

import com.estime.room.exception.DeadlineOverdueException;
import com.estime.room.exception.PastNotAllowedException;
import com.estime.shared.BaseEntity;
import com.estime.shared.DomainTerm;
import com.estime.shared.Validator;
import com.estime.shared.exception.InvalidLengthException;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.Index;
import jakarta.persistence.Table;
import java.time.LocalDateTime;
import lombok.AccessLevel;
import lombok.AllArgsConstructor;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.ToString;
import lombok.experimental.FieldNameConstants;

@Entity
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@AllArgsConstructor(access = AccessLevel.PRIVATE)
@Getter
@ToString
@FieldNameConstants(level = AccessLevel.PRIVATE)
@Table(indexes = {
        @Index(name = "idx_room_session", columnList = "session"),
        @Index(name = "idx_room_deadline", columnList = "deadline")
})
public class Room extends BaseEntity {

    private static final int TITLE_MAX_LENGTH = 20;

    @Column(name = "session", nullable = false)
    private RoomSession session;

    @Column(name = "title", nullable = false)
    private String title;

    @Column(name = "deadline", nullable = false)
    private LocalDateTime deadline;

    public static Room withoutId(
            final String title,
            final LocalDateTime deadline
    ) {
        validateTitleAndDeadline(title, deadline);
        final String trimmedTitle = title.trim();
        validateTitle(trimmedTitle);
        validateDeadline(deadline);
        return new Room(
                RoomSession.generate(),
                trimmedTitle,
                deadline
        );
    }

    private static void validateTitleAndDeadline(final String title, final LocalDateTime deadline) {
        Validator.builder()
                .add(Fields.title, title)
                .add(Fields.deadline, deadline)
                .validateNull();
    }

    private static void validateTitle(final String trimmedTitle) {
        if (trimmedTitle.isBlank() || trimmedTitle.length() > TITLE_MAX_LENGTH) {
            throw new InvalidLengthException(DomainTerm.ROOM, trimmedTitle);
        }
    }

    private static void validateDeadline(final LocalDateTime deadline) {
        if (deadline.isBefore(LocalDateTime.now())) {
            throw new PastNotAllowedException(DomainTerm.DEADLINE, deadline);
        }
    }

    public void ensureDeadlineNotPassed(final LocalDateTime currentDateTime) {
        if (deadline.isBefore(currentDateTime)) {
            throw new DeadlineOverdueException(session, deadline, currentDateTime);
        }
    }
}

```

# 2. application

비즈니스 로직이 위치하는 계층이다.
분리 과정에서 가장 외부 의존성이 깊게 침투해 있던 곳이기도 하다.
예를 들어, 디스코드 연동 로직들은 단순히 포트(인터페이스)로 추출하여 정리할 수 있었고, 이 부분은 비교적 단순한 작업이었다.

가장 고민했던 부분은 Repository 인터페이스의 위치였다.
DDD 관점에서는 Repository를 도메인 객체의 컬렉션처럼 바라보기 때문에 위에서 설명했듯 core에 두는 것이 자연스럽다고 생각했다.
하지만 조회 로직이 단순 CRUD를 넘어 페이징, 정렬, 필터링 등 비즈니스 로직에 가까운 수준으로 확장된다면, 이는 단순한 데이터 접근이 아니라 애플리케이션 로직으로 볼 수도 있다.

다만 현재 서비스에서는 대부분의 조회가 단순하거나 간단한 조건 수준에 머물러 있다.
따라서 현재는 core에 정의된 Repository 인터페이스로 충분하며, application에는 별도의 쿼리 전용 Repository가 존재하지 않는다.
향후 복잡한 조회나 도메인 규칙을 내포한 쿼리가 필요해진다면, QueryRepository처럼 명확히 구분된 이름으로 application에 별도 인터페이스를 추가할 계획이다.

```java
@Service
public class RoomApplicationService {
    private final RoomRepository roomRepository;
    private final PlatformMessageSender platformMessageSender;

    @Transactional
    public RoomCreateOutput createRoom(RoomCreateInput input) {
        Room room = Room.withoutId(input.title(), input.deadline());
        return RoomCreateOutput.from(roomRepository.save(room));
    }
}
```

```java
public interface PlatformMessageSender {
    void sendConnectedRoomCreatedMessage(String channelId, ...);
}
```

마무리 할 말이 없다. 포트는 application에 두고, infrastructure가 compileOnly로 참조할 수 있도록 한다.

# 3. infrastructure

가장 복잡하면서도 가장 매력적인 계층이다.
interface를 만족시키기 위해서라면 어떤 수단이든 동원할 수 있는, 말 그대로 현실을 다루는 곳 이다.
어쩌면 이 계층이야말로 내부 흐름을 실질적으로 담당하므로 가장 중요한 역할을 맡고 있다고도 볼 수 있다.

깔끔한 코드보다 더 우아한 것은, 명세를 충실히 이행하는 코드, 즉 외부를 위해 묵묵히 일하는 코드라고 생각한다.
이 계층은 DIP(Dependency Inversion Principle)의 철학이 실체화된 공간이다.
상위 계층이 정의한 포트를 구현하기 위해, 각종 기술과 환경 의존성을 다루며 끊임없이 문제를 해결한다.
당장의 명세에 충실히 복무하는 그 모습이 오히려 가장 섹시한 코드처럼 느껴진다.

분리 자체는 어렵지 않았다. 간단한 문제들을 해결하고 큰 고민도 없었다.

그렇지만 이번 분리 과정에서 하나 새롭게 느낀 점이 있다.
Controller 역시 infrastructure에 포함된다는 사실이다.
HTTP를 사용하는 REST 컨트롤러뿐만 아니라, GraphQL이나 gRPC와 같은 통신 방식으로 바뀐다 하더라도, 상위 계층(모듈)은 전혀 영향을 받지 않는다.
즉, 컨트롤러는 단지 요청을 받아 포트를 호출하는 어댑터일 뿐이며, 구체적 구현 기술이 바뀌더라도 infrastructure의 책임 안에서 해결된다.

단일 모듈로 개발했다면 아마 끝까지 체감하지 못했을 것이다. 감탄 한 번 했다.
컨트롤러도 결국 '어댑터'에 불과하다는 것을 진정으로 이해하게 되었다.

```java
public interface JpaRoomRepository extends JpaRepository<Room, Long> {
    Optional<Room> findBySession(RoomSession session);
}

@Repository
@RequiredArgsConstructor
public class RoomRepositoryImpl implements RoomRepository {
    private final JpaRoomRepository jpaRoomRepository;

    @Override
    public Optional<Room> findBySession(RoomSession session) {
        return jpaRoomRepository.findBySession(session);
    }

    @Override
    public Room save(Room room) {
        return jpaRoomRepository.save(room);
    }
}
```

```java
@Component
@RequiredArgsConstructor
public class DiscordMessageSender implements PlatformMessageSender {
    private final JDA jda;

    @Override
    public void sendConnectedRoomCreatedMessage(String channelId, ...) {
        jda.getTextChannelById(channelId).sendMessage(...).queue();
    }
}
```
