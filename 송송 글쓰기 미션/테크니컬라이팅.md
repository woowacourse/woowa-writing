안녕하세요 **Rilog. 백엔드 개발자 송송**입니다.

이번 글에서는 Rilog. 개발 시, 발생한 고아 객체를 처리하는 다양한 전략을 알아보고, Rilog.가 선택한 도구를 알아보는 시간을 가져보겠습니다.

## 1. 요구사항

> 이미지 업로드 기능이 필수입니다.

Rilog는 블로그 플랫폼 답게, 글 작성 기능을 지원합니다.
글 작성 시, BlockNote 기반 마크다운 에디터를 사용하고 이때 파일(이미지, PDF etc…)을 자유롭게 업로드할 수 있습니다. 또한 프로필 로고 이미지와 커버 이미지를 설정할 수 있습니다.

---

## 2. 문제

### 2-1. 문제 상황

> 이때, **고아 객체**(Orphan Object)가 발생할 수 있습니다.

BlockNote 기반 마크다운 에디터는 로컬 blob 이미지로 띄울 수 없습니다. 따라서 글 작성 중, 이미지를 함께 보려면 업로드와 동시에 저장된 이미지가 필요합니다.

이때, 여러 이미지를 포함한 글을 작성 중, 사용자가 이탈하면 어떻게 될까요? 이미지가 저장소에 존재하지만, 그 어느곳에서 참조하지 않는 상태가 됩니다.

어느곳에서도 참조하지 않지만 스토리지에 존재하는 객체를 고아 객체라고 하며,
Rilog에서 고아 객체는 주로 이미지, PDF같은 파일입니다.

- 고아 객체는 글 작성뿐만 아니라, 글 수정, 프로필 로고, 커버 이미지 수정에서도 발생합니다.

### 2-2. 원인

> 문제가 발생하는 원인은 **파일의 생명주기와 도메인의 생명주기가 일치하지 않기 때문**입니다.

파일 사용이 확정되는 시점과 게시글이 발행되는 시점은 생명주기가 같습니다. 그러나 파일이 업로드되는 시점이 다르다는 게 핵심 원인입니다.

Rilog에서 파일 업로드는 다음 순서로 이루어집니다.

```
Presigned URL 발급
→ 프론트엔드에서 S3로 파일 업로드
→ 업로드된 파일 URL을 본문에 포함
→ 게시글 저장
```

사용자가 글을 작성하면서 이미지를 확인하려면, 게시글을 저장하기 전에 이미지가 먼저 S3에 업로드되어야 합니다.

이때, 이미지 업로드와 게시글 저장은 하나의 작업처럼 보이지만 실제로는 서로 다른 저장소에서 이루어지는 별개의 작업입니다.

```
이미지 → S3
게시글 → Database
```

이미지 업로드는 성공했지만 게시글 저장에 실패할 수도 있고, 이미지 업로드 이후 사용자가 글쓰기 페이지에서 이탈할 수도 있습니다.

글 수정과 프로필 수정에서도 같은 문제가 발생합니다.

```
기존 이미지 A 사용
→ 새로운 이미지 B 업로드
→ 이미지 B로 변경
→ 이미지 A는 더 이상 참조되지 않음
```

## 3. 해결 방안. (다양한 전략)

그렇다면 고아 객체를 어떻게 처리할 수 있을까요?

---

### 3-1. 파일 제거

제가 가장 먼저 생각한 방법은 파일이 더 이상 필요하지 않은 순간, 바로 S3에서 삭제하는 것입니다.
(FE → S3)

예를 들어 에디터에서 이미지를 제거하면 프론트엔드가 삭제 API를 호출할 수 있습니다.

```
에디터에서 이미지 제거
→ 파일 삭제 API 호출
→ S3 객체 삭제
```

글 작성을 취소할 때, 현재까지 업로드한 파일을 모두 삭제하도록 만들 수도 있습니다.

하지만 사용자의 정상적인 행동만으로 모든 상황을 처리할 수는 없습니다. 사용자는 반드시 “글쓰기 취소” 버튼을 누르고 이탈하지 않기 때문이죠.

- 브라우저를 종료할 수 있습니다.

- 탭을 닫을 수 있습니다.

- 네트워크가 끊길 수 있습니다.

- 프론트엔드 애플리케이션에 오류가 발생할 수 있습니다.

단순한 게시글 작성에서도 이런 엣지케이스가 있으며, 게시글을 수정했을 때, 삭제될 파일과 생성될 파일까지 고려하면 더 복잡해집니다.

따라서 즉시 삭제 방식은 불필요한 파일을 빠르게 줄이는 보조 수단으로는 사용할 수 있지만, 이것만으로 모든 고아 객체를 처리하기는 어렵다고 판단했습니다.

### 3-2. 파일 정보를 DB에서 관리

두 번째 방법은 업로드된 파일을 별도의 테이블에서 관리하는 것입니다. BackEnd가 주도권을 가져올 수 있는 방식이라고 생각합니다.

파일을 처음 업로드하면 `TEMPORARY` 상태로 저장하고, 게시글이나 프로필에서 사용되면 `CONFIRMED` 상태로 변경합니다.

```
파일 업로드
FE → S3 이미지 저장 후 객체 주소 얻음
FE → 객체 주소 전달 → BE → DB에 TEMPORARY 저장

게시글 발행
→ 게시글 Content에서 이미지 객체 추출 
→ DB TEMPORARY → CONFIRMED 변경

고아 이미지 처리
→ DB의 TEMPORARY를 찾아 S3에 삭제 요청 + DB 삭제 (스케줄링)
```

게시글 작성 중 생겨난 `TEMPORARY 파일`을 Server가 DB에 저장하여 영구적으로 알 수 있습니다. (S3를 탐색하지 않고)
그리고 게시글 발행 시 `TEMPORARY 파일`을 `CONFIRMED`로 변경하여, 사용 확정을 표시할 수 있습니다.

단, 두 가지 귀찮은 점이 있습니다.

1. S3와 DB 정합성을 맞출 방법 강구.

1. 주기적으로 DB에서 TEMPORARY 파일을 탐지하는 스케줄링 구현

즉, 새로운 관리 대상이 생겨납니다.

게시글 본문(Content)을 JsonB 타입으로 저장하고 있고, 해당 데이터에 S3 객체 경로가 포함됩니다.
별도의 Table로 관리한다면 **S3와 DB 정합성**을 맞춰야 하며, **JsonB 타입 Content와 File Table의 정합성**까지 맞춰야 합니다.

→ 현재 빠른 개발 목표로 하고 있는 입장에서 부담스러운 선택이라고 생각했습니다.

### **3.3 임시, 확정 경로 분리하기.**

파일을 처음 업로드할 때는 임시 경로에 저장합니다.

```javascript
파일 업로드
FE → temporary/images/{fileId}.png
```

게시글이나 프로필에서 실제 사용이 확정되면 영구 경로로 이동합니다.

```javascript
FE 
→ temporary/images/{fileId}.png가 포함된 JsonB를 전송

BE 
→ Content에서 temporary/images/{fileId}.png를 찾음
→ S3에게 confirmed/images/{fileId}.png로 이동 요청
→ Content의 파일 경로를 confirmed로 바꾼 뒤, JsonB를 DB 저장.
```

일정 시간이 지나도 임시 경로에 남아 있는 파일은 고아 객체로 판단하여 삭제할 수 있습니다.
이때, 삭제 방법은 직접 스케줄링을 구현하거나 S3의 생명주기 만료 규칙을 `temporary/`에 적용할 수 있겠죠.

고아 이미지 처리를 위해 Server가 집중할 부분은 Content에서 **파일 객체 주소 찾고**, **S3에게 이동 요청**을 보내는 것 뿐이라 개발 부담도 적다고 생각합니다. 특히 관련 레퍼런스도 많아 참고하기 편하기도 했습니다.

그러나, 한가지 문제가 있습니다.
바로 Client에게 받은 Content에는 temporary **경로**로 저장되어있다는 문제죠!

성공적으로 발행된 게시글 이미지를 영구적으로 보여주기 위해서는, 경로 이동의 정합성이 필요합니다.
(경로 이동(S3)과 TEMP → CONFIRMED의 이동이 확실히 보장되어야함)

추후 경로 방식을 사용해 thumbnail과 original 객체를 분리하려고 했기 때문에, 경로 관리 대상이 추가되는 건 부담스러웠습니다. (thumbnail, temporary, confirmed 세가지 경로를 관리)

- **S3 객체의 생명주기**와 **이미지 효율**을 위한 썸네일, 원본 방식은 탄생 배경이 다른데 경로로 함께 관리하는 게 어색하게 느껴지기도 했습니다.

### 3-4. S3 TAG 전환

네 번째 방법은 S3 객체의 태그를 이용해 파일 상태를 표현하는 것입니다.

파일을 처음 업로드할 때 TEMPORARY 태그를 지정하고, 게시글이나 프로필에서 사용이 확정되면 CONFIRMED 태그로 변경합니다.

```javascript
status=TEMPORARY
status=CONFIRMED
```

더 이상 사용하지 않는 파일은 다시 `TEMPORARY` 상태로 변경합니다.

```javascript
TEMPORARY
    ↓ 사용 확정
CONFIRMED
    ↓ 참조 제거
TEMPORARY
```

그리고 S3 생명주기 규칙(Lifecycle Rule)을 이용하여 일정 기간 이상 `TEMPORARY` 상태인 객체를 자동으로 삭제합니다.

이 방식의 장점은 임시 경로와 영구 경로를 분리하는 방식과 달리 **객체 경로를 변경하지 않습니다.
**따라서 파일의 URL을 그대로 유지하면서 상태만 변경할 수 있다는 장점이 있습니다.

## 4. Rilog.의 선택

Rilog에서는 **S3 객체 태그와 Lifecycle을 이용한 지연 삭제 전략**을 선택했습니다.
자세한 설명과 함께하겠습니다

### 4-1. S3 객체 태그 생명 주기

파일을 업로드한 것만으로는 실제 사용이 확정됐다고 볼 수 없습니다.
따라서 업로드 직후의 파일은 `TEMPORARY` 상태로 시작합니다.

```javascript
파일 업로드
→ TEMPORARY
```

게시글, 초안 또는 블로그 프로필에 파일이 연결되면 `CONFIRMED` 상태로 변경합니다.

```javascript
도메인에 파일 연결
→ CONFIRMED
```

수정 과정에서 파일의 참조가 제거되거나 도메인 자체가 삭제되면 다시 `TEMPORARY` 상태로 변경합니다.

```javascript
도메인에서 파일 분리
→ TEMPORARY
```

마지막으로 일정 기간 동안 `TEMPORARY` 상태인 객체는 S3 Lifecycle Rule(생명주기 규칙)이 삭제합니다.

```javascript
TEMPORARY
→ 유예 기간
→ S3 Lifecycle 삭제
```

이때 애플리케이션이 파일을 즉시 삭제하지 않는 이유는 정상적인 파일을 잘못 삭제할 가능성을 줄이기 위해서입니다. 덕분에 게시글 저장과 S3 태그 변경 사이에 일시적인 오류가 발생하더라도, 유예 기간 안에 상태를 복구할 수 있습니다.

또한 별도의 파일 관리 테이블을 만들지 않고 S3 객체 자체에 상태를 표현할 수 있습니다. 이 덕분에 객체 경로를 변경하지 않으며 게시글과 프로필에 저장된 URL도 그대로 유지할 수 있습니다.

### 4-2. S3 Tag 비용

[Amazon S3, S3 객체 태그 지정 요금 35% 인하 - AWS](https://aws.amazon.com/ko/about-aws/whats-new/2025/03/amazon-s3-reduces-pricing-object-tagging/)

비용 측면에서도 이 방식을 검토했습니다. 이미지를 S3에 보관하는 동안에는 스토리지 비용이 발생하며, 객체 태그를 사용하면 태그 저장 비용과 태그를 설정하거나 변경하는 API 요청 비용이 추가됩니다.

대신 태그를 이용해 일정 기간이 지난 고아 객체를 삭제하면, 해당 이미지에 앞으로 발생할 스토리지 비용을 줄일 수 있습니다. 따라서 태그와 요청에 드는 추가 비용을 감수하더라도, 사용하지 않는 이미지를 지속적으로 정리할 수 있다는 점에서 이 방식을 선택했습니다.

### 4-3. 간단한 구현

S3 Tag 방식을 사용하면 고아 이미지 처리를 매우 빠르게 해결할 수 있다고 판단했습니다.

서버단에서 **고아 이미지 처리**를 위해 구현해야 하는 부분은 딱 두가지이기 때문입니다.

1. S3 TAG 전환 호출 코드

1. 게시글의 Content에서 처리해야하는 파일 객체 추출

때문에 Spring Boot Application에서 구현할 코드량이 적고, 실제로 많지 않았습니다.

## 5. 재시도

실제 구현을 하고 보니, S3 TAG 방식은 완벽한 방식은 아니었습니다.

S3 TAG 전환이 실패하는 경우를 고려해야 했기 때문입니다. 이는 AWS S3라는 외부 인프라를 사용하기로 한 순간 필연적으로 고민해야 할 부분이죠.

### 5-1. 재시도 시스템이 필요한 이유.

예를 들어 게시글 발행은 성공했지만, S3 TAG를 `CONFIRMED`로 변경하지 못할 수 있습니다.

> 게시글 저장 성공
> → S3 TAG 변경 실패
> → 사용 중인 파일이 TEMPORARY로 남음

게시글에서는 정상적으로 이미지를 사용하고 있지만, S3 객체는 계속 **TEMPORARY** 상태로 남아있게 됩니다.
이 상태가 오래 유지되면 AWS Lifecycle Rule에 의해 정상적으로 사용 중인 파일이 삭제될 수도 있습니다.

반대 상황도 발생할 수 있습니다.

> S3 TAG를 CONFIRMED로 변경
> → 게시글 저장 실패 또는 DB Transaction Rollback
> → 어디에서도 참조하지 않는 CONFIRMED 객체 발생

이 경우 파일은 실제 도메인에서 사용하지 않지만 **CONFIRMED** 상태이기 때문에 Lifecycle Rule의 삭제 대상에서 제외됩니다. 고아 객체가 삭제되지 않는 문제가 발생합니다.

결국 DB와 S3는 **서로 다른 저장소**이기 때문에 하나의 Transaction으로 완벽하게 묶을 수 없기 때문에 발생하는 문제입니다. (**Database Transaction ≠ S3 Object TAG 변경**)

### 5-2. 대응책

그렇다면 TAG 변경에 실패했을 때 어떻게 해야 할까요?

S3 TAG 전환은 같은 요청을 여러 번 보내도, 결과가 같습니다. 따라서 TAG 전환은 비교적 안전하게 다시 요청할 수 있는 작업이라고 판단했습니다.

물론 “다시 요청할 수 있다”와 “자동으로 다시 요청한다”는 다른 이야기이며, 실패한 요청을 자동으로 처리(재시도)하려면 여러 방법을 고민해야합니다.

이번 글은 고아 이미지를 처리하는 여러가지 방법에 대해 Rilog가 고민한 흔적을 남기기 위한 목적이므로, 재시도 처리에 대한 자세한 내용은 추후 다뤄보도록 하겠습니다.

처음에는 고아 객체를 단순히 “사용하지 않는 파일” 정도로 생각했는데요...

따라서 파일이 필요 없어지는 순간 바로 삭제하면 해결할 수 있을 것이라 생각했습니다.

하지만 실제로 고민해 보니 고아 객체는 생각보다 단순하지 않고, **파일이 업로드되는 시점**과 **파일 사용이 확정되는 시점**의 정합성을 맞춰야하는 문제였습니다.

이를 해결하기 위해 다음과 같은 전략을 살펴보았구요.

1. 파일이 필요 없어지는 순간 즉시 삭제

1. 파일 정보를 별도의 DB Table에서 관리

1. 임시 경로와 확정 경로를 분리

1. S3 객체 TAG를 이용한 상태 관리



각 전략은 분명한 장점이 있었지만, Rilog의 현재 상황에서는 그만큼의 단점도 존재했습니다.

- DB에서 파일을 관리하면 명확한 상태를 가질 수 있지만 새로운 관리 대상과 정합성 문제가 생김.

- 임시 경로와 확정 경로를 분리하면 상태를 직관적으로 표현할 수 있지만, 객체 이동에 따라 Content 내부의 URL까지 변경해야 함.



Rilog는 객체 경로를 변경하지 않고, 별도의 File Table도 만들지 않으면서 파일의 상태를 표현하고 싶었습니다.
따라서 다음과 같이 S3 객체 TAG를 이용한 생명주기를 선택했습니다.



이 방식이 모든 서비스에서 가장 좋은 정답이라 생각하지는 않습니다.
파일을 여러 도메인에서 공유하거나 파일별 소유권과 사용량을 관리해야 한다면 별도의 File Table이 더 적합할 수 있습니다.

다만 빠르게 기능을 개발하고 있는 현재 Rilog에서는 S3 TAG 방식이 구현 복잡도와 얻을 수 있는 효과 사이에서 가장 합리적인 선택이라고 판단했습니다.



이번 글에서는 고아 객체가 발생하는 원인과 이를 처리할 수 있는 여러 전략을 살펴보았습니다.

다음 글에서는 실제 Rilog의 S3 객체 구조를 확인하고, 도메인에서 사용하는 파일을 추출하여 `TEMPORARY`와 `CONFIRMED` 태그를 변경하는 `TagAssetsLifecycle` 구현 과정을 다뤄보겠습니다.

### 3. Lifecycle Interface

#### 3-1. 행동 관찰

게시글에서 발생하는 TagAssets 변경은 크게 세가지입니다.

1. 게시글 발행으로, 본문에 있는 File, Image사용을 **확정**하는 경우

1. 게시글 수정으로, 본문에 있는 File, Image가 **변경**된 경우

  - 기존 본문에서 추가된 경우

  - 기존 본문에서 삭제된 경우

1. 게시글 삭제로, 본문에 있는 File, Image가 **삭제**되는 경우

따라서 **확정**, **변경** 그리고 **삭제** 총 3가지 행동을 관찰할 수 있으며, 이에 **Interface**를 설계했습니다.

#### 3-2 Interface Code

다음과 같이 **확정**, **변경** 그리고 **삭제** 계약을 나타내는 Lifecycle이라는 Interface를 만들었습니다.

```java
public interface TagAssetsLifecycle {  
  
    void attach(TagAssets assets);  // TEMPORARY -> CONFIRMED
  
    void synchronize(TagAssets previous, TagAssets current);  
  
    void detach(TagAssets assets);  // CONFIRMED -> TEMPORARY 
  
}
```

#### 3-3. Lifecycle 구현체

`TagAssetsLifecycle`의 구현체는 게시글의 행동을 S3 Object Tag 상태로 변환합니다.

| 행동 | S3 Object Tag 변화 |
| --- | --- |
| `attach` | 사용이 확정된 자산을 `CONFIRMED`로 변경 |
| `synchronize` | 추가된 자산은 `CONFIRMED`, 제거된 자산은 `TEMPORARY`로 변경 |
| `detach` | 연결이 해제된 자산을 `TEMPORARY`로 변경 |

```java
public class S3TagAssetsLifecycle implements TagAssetsLifecycle {

    private final S3ObjectTagger objectTagger;

    @Override
    public void attach(TagAssets assets) {
        tag(assets, CONFIRMED);
    }

    @Override
    public void synchronize(TagAssets previous, TagAssets current) {
	    // TagAssets 두 객체가 변화파악을 협력할 수 있도록 changesTo()도메인 로직 추가
        TagAssetChanges changes = previous.changesTo(current); 
        
        tag(changes.added(), CONFIRMED);
        tag(changes.removed(), TEMPORARY);
    }

    @Override
    public void detach(TagAssets assets) {
        tag(assets, TEMPORARY);
    }
}
```

게시글 수정에서는 변경 전후의 자산을 비교해 실제로 추가되거나 제거된 자산만 처리합니다.

```javascript
수정 전: [A, B]
수정 후: [B, C]

A: 제거됨 → TEMPORARY
B: 유지됨 → 변경 없음
C: 추가됨 → CONFIRMED
```

#### 3-4. S3ObjectTagger

이제 AWS S3에 특정 Object Tag를 변경하는 API를 호출해야합니다.
단순 API 호출은 aws sdk 의존성에 잘 추상화되어있어, 그대로 사용하면 됩니다.

단, S3ObjectTagger가 **TAG 변경**을 위해 필요한 건 뭔지 생각해야 하고 그건 바로 **Object 주소**와 **Tag값**입니다.

lifecycle에서는 확정, 변경, 삭제에 따라 각각 attach, synchronize, detach로 의미가 존재합니다. 
그러나, S3ObjectTagger는 Object의 TAG를 변경할 뿐, 그 변경의 의미를 알 필요는 없습니다. 
따라서 다음과 같이, 하나의 행동이면 충분합니다.

```java
public class S3ObjectTagger {  
  
    private final S3Client s3Client;  
    private final S3Properties properties;  
    
    // 실제 코드에서는 S3TagTarget이라는 VO로 포장
    private void changeS3ObjectTag(String objectKey, TagStatus tagStatus) {
        try {  
            s3Client.putObjectTagging(PutObjectTaggingRequest.builder()  
                    .bucket(properties.bucket())  
                    .key(objectKey)  
                    .tagging(tagStatus)  
                    .build());  
        } catch (SdkException exception) {  
			// 예외 처리. 
        }  
    }  
  
}

// 실제 사용한 VO
public record S3TagTarget(  
        String key,  
        TagStatus tagStatus  // TEMPORARY, CONFIRMED
) {
}
```

#### 3-5. 게시글 발행, 수정, 삭제에 적용.

이렇게 코드 만들어 놓고 끝이 아니라, 실제 게시글 비즈니스 로직에 적용을 해야 동작하겠죠?

```java
public class PostService {  
  
    // 기타 의존성 생략
	private final TagAssetsLifecycle tagAssetsLifecycle 
	
    @Transactional  
    public PostPublishResult publish(PostSaveCommand command, Long requesterId) {  
        // 기타 로직 생략
        Post published = postRepository.save(post);  

        // 저장된 게시글에서 TagAssets 추출 후, attach()
        tagAssetsLifecycle.attach(published.getTagAssets());
        return PostPublishResult.of(published, publishingBlog);  
    }

	@Transactional  
	public PostUpdateResult update(PostUpdateCommand command, Long postId, Long requesterId) {  
	    TagAssets previousTagAssets = post.getTagAssets(); // 수정 전 TagAssets
	  
	    post.update(command.toDetail(), targetBlog, chapter);  
	  
	    TagAssets updatedTagAssets = post.getTagAssets();  // 수정 후 TagAssets
	    tagAssetsLifecycle.synchronize(previousTagAssets, updatedTagAssets);
	    return PostUpdateResult.of(post, targetBlog);  
	}

}
```

- 게시글 발행 후, TagAssets를 추출해서 Lifecycle 구현체에게 전달 (**attach()**)

- **게시글 수정 전, TagAssets**과 **게시글 수정 후, TagAssets**를 Lifecycle 구현체에게 전달. (**synchronize()**)

- 게시글 삭제 전, TagAssets를 Lifecycle 구현체에게 전달 (**detach()**)

### 5. 실제 적용 후 취약점 발견.

개발 서버에서 이미지가 사용되는 로직에 TAG 전환이 이루어지는 지 확인하고 운영 환경에 적용했습니다.

당시 우아한 테크 코스 크루 몇명을 대상으로 운영하고 있었는데요.
그 중 한 크루(**아론**)가 취약점을 발견해주었습니다.

#### 5-1. 이미지 주소 복사 악용

이미지 주소는 게시글 본문에 그대로 저장되기 때문에 다른 사람의 **이미지 주소**를 복사해 자신의 글에 사용할 수 있었습니다.

문제는 복사한 이미지를 사용한 게시글을 삭제할 때 발생했습니다.

![image.png](https://techcourse-project-2026.s3.ap-northeast-2.amazonaws.com/rilog/images/originals/1-bb1f7296-3d02-4457-b1e0-e60e20e0e4b2.png)

결론적으로

> 사용자 B는 자신의 게시글만 삭제했지만, 그 결과 사용자 A가 소유한 이미지까지 삭제 가능!

#### 5-2. 해결방안

문제가 발생하는 핵심 원인은 **이미지 주소 복사**와 **소유권**입니다.
이미지 자체를 복사하여, ctrl + v로 올릴 수 있지만, 이미지 주소 자체를 복사하여 올릴 수 있기 때문입니다. 그렇다고 **사용자가 이미지 주소 복사하는 걸 막을 순 없겠죠.**

따라서 **소유권**을 **부여**하기로 결정했습니다.

방법은 단순한데요. 
S3에 객체를 업로드할 때, 맨 앞 prefix에 소유자의 ID를 추가해주는 겁니다.
그리고 S3 Object Tagging을 수행할 때 마다, Token에 있는 requesterId와 ObjectKey의 prefix를 비교하는 거죠.

```
변경 전
images/originals/{uuid}.png

변경 후
images/originals/{userId}-{uuid}.png
```

이러면 `images/originals/A-{uuid}.png`로 업로드한 S3 Object를 사용자 B가 주소 복사한 뒤 삭제하더라도, prefix 검증에 실패하여 S3 Object Tagging을 호출하지 않습니다. 

TEMPORARY 전환이 이루어지지 않는거죠.

> 1, 2편에서는 TAG 기반의 블로그 서비스에서 발생하는 고아 상태 이미지를 처리한 방법에 대해 서술했다.
> 이번 글 이후부터는 발생한 문제와 해결방안에 대해서 이야기하려 합니다.



## 1. 응답 지연

게시글 발행 후, 이미지 사용을 확정(CONFIRMED)한다.

따라서 S3로 ObjectTag를 변경하는 API를 호출한다.



게시글 발행, 수정, 삭제라는 주 관심사와 이미지 TAG 변경이라는 외부 API가 하나의 트랜잭션에 묶여 있다.

실제로 이미지 20개가 포함된 경우, 응답이 약 800ms 지연되었다. (API 응답시간 **0.990ms**)



게시글 발행이 조금 느려도 무슨 상관이겠다만, 실제로 관련된 문제가 있었다.

게시글 발행 처리가 되고 있는지, 아닌지 몰랐던 크루가 발행 버튼을 한 번 더 눌러 글이 2개 생겨난 적이 있기 때문이다.

물론 이 문제는 근본적으로 멱등성을 보장하지 않았기 때문이다. 

하지만, **사용자가 발행 버튼을 다시 누른 이유**는 발행처리가 되고 있는지 아닌지 몰랐다는 점과 발행처리가 느려서 그 페이지에 여전히 머물러있었기 때문이라는 복합적인 이유가 있다. 

즉 멱등성을 보장하더라도, 응답이 느리면 **사용자는 답답함을 느낀다**는 점이다. 

> 그래서 이번 글에서는 **응답 지연** 문제를 다룰 예정이다.



즉, 주 관심사 로직과 외부 API가 하나의 트랜잭션에 묶여 응답이 지연되는 문제를 개선해보고자 한다.

## 2. 개선안

요청이 외부 API의 응답을 기다려, 지연된게 핵심이다.

![image.png](https://techcourse-project-2026.s3.ap-northeast-2.amazonaws.com/rilog/images/originals/1-63933a37-8b5b-4ca2-a125-b5166e0f862d.png)

따라서 개선안은 외부 API의 응답을 기다리지 않고 바로 응답, 외부 API는 별도로 수행하도록 **분리**하면 된다.

S3 Tagging 요청 메서드가 별도 스레드에서 수행하도록 해당 메서드에 **@Async**를 붙이면 된다.



### 2-1. @Async

**@Async**를 사용하면 무엇을 얻고 무엇을 잃을까?
더이상 외부 API를 기다리지 않는 게 가장 큰 이점이다. 



@Async를 사용하니 평균 응답 속도는 190ms가 나왔다. TAG 변경 요청으로 추가된 800ms 지연이 없어졌으니 당연하다. 



그러면 무엇을 잃었을까 내 생각은 두 가지이다. 



첫번째로 기존 **트랜잭션과 전혀 상관이 없어졌다**는 점이다. 그래서 트랜잭션이 롤백되더라도, 비동기로 동작하는 @Async 메서드를 되돌릴 수 없었다. 그럼에도 이는 심각한 문제가 아니다. DB에 문제가 발생하여 트랜잭션이 롤백되거나 실패할 일이 거의 없기 때문이다. 



두번째는 TAG 변경이 가지는 **순서적 의미**가 사라진다는 점이다. 이 역시, 트랜잭션과 전혀 상관이 없어졌기에 발생한 문제다. 의미상 사용이 **확정**되거나 **철회**된 이미지에만 TAG 변경이 일어나야한다. 
그러나 하지만 트랜잭션과 완벽히 분리하면서 이 **의도가 사라졌다.** 



단순히 @Async를 사용하는 게 마음에 들지 않았던 건 두번째 이유가 크다.
솔직히 **별도 TAG 변경 API**를 만들어서 프론트가 호출하는 것과 큰 차이가 없다고 생각했다. 

비동기 처리는 기존 트랜잭션으로부터 부 관심사를 완벽히 분리할 수 있게 도와준다. 그러나, 부 관심사가 가지는 의도도 함께 사라지는 게 싫었다.



**CONFIRMED**, **TEMPORARY** 는 단순히 “태그 변경 요청을 받았다”는 뜻이 아니라 다음 의미를 가진다.

> 커밋된 게시글이 이 이미지를 사용하고 있다.

> 커밋된 게시글이 이 이미지를 더이상 사용하지 않는다.

따라서 **CONFIRMED**, **TEMPORARY** 변경하는 작업은 게시글이 커밋된 이후에 일어나야 한다.



### 2-2. TransactionalEventListener

그래서 이 방법을 선택했다.

**@TransactionalEventListener**는 이름 그대로 트랜잭션의 상태에 따라 이벤트를 처리할 수 있게 도와준다.

```java
@Transactional
public PostPublishResult publish(...) {
    Post post = postRepository.save(...);

    tagAssetsPublisher.attach(post.getTagAssets());

    return PostPublishResult.from(post);
}
```

게시글을 저장하는 트랜잭션에서는 S3 API를 직접 호출하지 않는다.



대신 **“이 이미지 사용을 확정한다”**는 이벤트만 발행한다.

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handle(TagAssetsEvent.Attach event) {
    lifecycle.attach(event.assets());
}
```

그리고 기존 트랜잭션을 COMMIT하고 이벤트를 받아 처리하도록 돕는 게 `AFTER_COMMIT`이다.

이름 그대로 게시글 트랜잭션이 **커밋된 이후에만** 이벤트를 처리한다.



트랜잭션이 롤백되면 이벤트 리스너는 실행되지 않는다.

```
게시글 저장 성공
→ 트랜잭션 커밋
→ 이미지 사용 확정 이벤트 처리
→ S3 태그를 CONFIRMED로 변경
```



반대로 게시글 저장이 실패하면 다음과 같이 끝난다.

```
게시글 저장 실패
→ 트랜잭션 롤백
→ 이벤트 처리 안 함
→ S3 태그 변경 안 함
```

앞에서 `@Async`만 사용했을 때 사라졌던 **순서**를 다시 표현할 수 있게 됐다.



### 2-3. 이벤트와 응답지연

**이벤트만 사용하면 기존 문제인 응답 지연이 해결될까?**

> 그렇지 않다.

**@TransactionalEventListener**를 사용한다고 해서 이벤트가 자동으로 별도 스레드에서 처리되지 않는다.

**AFTER_COMMIT**은 이벤트의 **실행 시점**만 커밋 이후로 옮긴다. 이벤트 리스너가 동기적으로 실행되면 요청 스레드는 여전히 S3 응답을 기다려야 한다.

그래서 이벤트 리스너에 **@Async**를 함께 사용했다.

```java
@Async(S3_TAGGING_EXECUTOR)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handle(TagAssetsEvent.Attach event) {
    lifecycle.attach(event.assets());
}
```

두 애노테이션이 해결하는 문제는 서로 다르다.

- @TransactionalEventListener(AFTER_COMMIT)은 언제 실행할 것인지 결정한다.

- @Async는 어느 스레드에서 실행할 것인지 결정한다.

AFTER_COMMIT을 통해 게시글 저장이 성공한 이후에만 태깅한다.

@Async를 통해 요청 스레드는 S3 태깅이 끝날 때까지 기다리지 않는다.



결과적으로 흐름은 다음과 같이 변경됐다.

![image.png](https://techcourse-project-2026.s3.ap-northeast-2.amazonaws.com/rilog/images/originals/1-fcec4f92-ab7c-4ae1-948a-aa9872bc10ec.png)

결과적으로 **@Async**를 버리지도 않았다.



## 3. 의문

여기까지 구현하면 응답 지연은 해결된다.

실제로 이미지 20개가 포함된 게시글의 평균 응답 시간은 약 **990ms**에서 **190ms**로 줄었다.
약 800ms가 걸리던 S3 태깅을 요청 흐름에서 분리했으니 당연하다.

하지만 새로운 문제가 생겼다.

이제 사용자는 게시글 발행 성공 응답을 먼저 받는다.

그 이후 비동기 태깅이 실패하더라도 사용자에게 실패를 전달할 수 없다. 

```
게시글 커밋 성공→ 사용자에게 발행 성공 응답→ 비동기 태깅 실패
```

CONFIRMED 변경에 실패하면 사용 중인 이미지가 계속 TEMPORARY로 남는다.

반대로 이미지 사용을 철회하면서 TEMPORARY 변경에 실패하면 더 이상 사용하지 않는 이미지가 CONFIRMED로 남는다.



이 문제를 해결하려면 자연스럽게 **재시도**가 떠오르며, 이벤트 소실까지 막기 위해 더 강한 보장이 필요하다면 **Outbox Pattern**도 생각할 수 있다.

### 3-1. 재시도를 추가할까?

S3 태깅이 실패하면 몇 번 더 요청하도록 만들 수 있다. 지수 백오프를 적용하거나, 실패한 객체를 별도의 큐에 넣고 다시 처리하는 방법도 있다. 그러나 비동기로 분리했다는 이유만으로 재시도를 바로 추가하고 싶지는 않았다.



재시도를 추가하면 다음 항목을 결정해야 하고 고려할 사항이 많다.

- 어떤 오류를 재시도할 것인가?

- 최대 몇 번 재시도할 것인가?

- 재시도 간격은 어떻게 정할 것인가?

- 최종 실패한 이미지는 어떻게 복구할 것인가?

- 재시도 중 애플리케이션이 종료되면 어떻게 할 것인가?

실제로 문제가 발생하는지 확인하지 않고 구현하기에는 결정해야 할 것이 많았다.



그래서 먼저 **현재 방식**이 **예상한 부하**에서 **어느 정도 동작하는지 실험**했다. 정확히는 정말 **재시도를 도입**해야할 상황인지 궁금했다.

실험 조건으로 이미지 100개를 준비했고 5명의 가상 사용자가 서로 다른 이미지 20개씩을 담당했다.

각 사용자는 이미지 20개를 CONFIRMED로 변경한 뒤, 다시 TEMPORARY로 변경했다.

```
5명 × 이미지 20개
= 이미지 100개

CONFIRMED 요청 5건
+ TEMPORARY 요청 5건
= HTTP 요청 10건

이미지 100개 × 태그 변경 2회
= S3 태깅 200회
```

실험 결과 **10건의 HTTP 요청은 모두 성공했다.**

HTTP 상태와 공통 응답의 상태를 검사한 20개의 check도 모두 통과했다.

실험이 끝난 뒤 이미지 100개의 태그를 다시 조회했을 때 최종 상태는 모두 TEMPORARY였다.

| 지표 | 결과 |
| --- | --- |
| HTTP 요청 | 10건 |
| HTTP 요청 실패 | 0건 |
| 전체 check | 20개 |
| 성공한 check | 20개 |
| 평균 응답 시간 | 792.91ms |
| p95 응답 시간 | 840.77ms |
| 최대 응답 시간 | 841ms |
| 최종 상태가 정상인 이미지 | 100개 |

해당 실험 이후에도 일주일간 시간이 날때마다 돌려봤는데 모두 성공했다. 

단순히 수치상으로 봤을 때, 5명이 동시에 게시글을 발행하더라도 S3가 이상한게 아니라면 TAG 요청은 정상작동한다.





물론 이 실험이 TAG 태깅은 무조건 성공한다는 걸 보장하지 않는다. 

네트워크 단절, AWS 스로틀링 등등 다양한 환경에서 실험하지도 않았고 장애는 언제든 일어날 수 있기 때문이며, 심지어 내가 짠 코드가 아니라 AWS S3라는 외부 서비스니까...



> 그럼에도 **현재 예상 규모**에서 **재시도**를 애플리케이션 Layer에서 **직접** **구현해야 할 근거**는 찾지 못했다.

또한 AWS SDK에서 기본으로 3회 재시도를 해주기 때문에, 더욱 현재 재시도 구현은 이르다고 판단했다. 

대신 태깅이 실패하는 경우 예외 로그를 남기고 그라파나 알림을 보내 팀원이 인지할 수 있도록 보완했다.



만약 이 로그가 반복되면 그때 재시도를 추가하자고 합의했다.

### 3-2. Outbox Pattern은 왜 사용하지 않았을까?

**@TransactionalEventListener**에도 빈틈은 있다.

게시글 트랜잭션이 커밋된 직후 애플리케이션이 종료되면??

```
게시글 커밋 성공
→ 애플리케이션 종료
→ 비동기 이벤트 처리되지 않음
```

현재 이벤트는 메모리에 존재한다. 따라서 애플리케이션이 종료되면 아직 처리되지 않은 이벤트가 사라질 수 있다.



Outbox Pattern을 사용하면 이 문제를 줄일 수 있다.
게시글을 저장하는 트랜잭션에서 이벤트도 Outbox 테이블에 함께 저장한다.

```
게시글 저장
+ Outbox 이벤트 저장
→ 트랜잭션 커밋
→ 별도 작업자가 이벤트 조회
→ S3 태깅
→ 처리 완료 기록
```

게시글과 이벤트가 하나의 DB 트랜잭션에 저장 돼, 태깅 작업이 메모리에서 사라지는 문제를 막을 수 있다.

하지만 Outbox를 도입하면 단순히 테이블 하나가 추가되는 것으로 끝나지 않는다.

Outbox 테이블을 주기적으로 읽어 작업하는 코드, 같은 이벤트 중복 처리, 재시도 횟수, 그럼에도 실패하는 이벤트 등등 고려할 사항이 많다.

> **Rilog.는** **블로그 서비스**를 만드는 거지 **메세지 전달 시스템을 만드는 게 아니니까...**

게시글 응답에서 S3 태깅을 분리하면서, 게시글 커밋 이후에 태깅한다는 의미를 유지하는 것이 목적이었다.

실험 범위에서는 태깅 실패와 이벤트 유실도 발견되지 않았다.

따라서 아직 발생하지 않은 문제를 위해 Outbox와 작업자를 먼저 운영하기보다, 실패 로그를 관찰하면서 실제 문제가 확인될 때 도입하기로 했다.

다만 재시도 실험이 Outbox가 필요 없다는 사실까지 증명한 것은 아니다. 현재 확인된 위험과 MVP의 규모에 비해 운영 비용이 크다고 판단해 보류했다. 서비스가 매우 커지면 그때 도입해도 충분하다고 판단했다!

솔직히 아웃박스 패턴은 현재 규모상 **허상**이라 생각하기도 했다.



## 4. 결과 

기존에는 게시글 발행, 수정, 삭제 요청이 이미지 태깅 완료를 기다리느라, 이미지 20개를 처리하는 데 약 800ms가 추가됐고, 게시글 발행 API의 응답 시간은 약 990ms였다.

단순 수치 말고도 다음과 같은 의미도 얻었다.

- 게시글이 커밋된 경우에만 이미지 사용을 확정한다.

- 게시글 요청은 S3 태깅을 기다리지 않는다.



물론 커밋 이후 애플리케이션이 종료되면 이벤트가 유실되며, TAG 실패에 복구 로직이 없다. 아직 관찰되지 않고 현재 트래픽 상황에서 매우 희박한 실패를 모두 예상해 복잡한 구조부터 만드는 대신, 현재 필요한 보장까지만 구현하기로 했다.

그리고 최소한의 방어로 예외 로그를 남기도록 했다.



솔직히 예외 로그가 많이 발생하더라도, 홈서버에 n8n을 돌리고 있기 때문에, 별도 재시도 로직을 n8n에 구축할 수 있을 거 같다. 그건 그때가서 생각해봐야지...!
