# 코드는 AI가 써주는데, 우리는 무엇을 결정해야 할까? 우리 팀의 기술 선택과 우선순위 결정기

최용준

## AI로 구현할 수 있는 일이 늘어난 뒤에 남은 질문

저희는 개발자 교육 과정인 우아한테크코스에서 팀 프로젝트로 Devica를 만들었습니다. Devica는 사용 목적에 맞는 전자제품을 고르기 어려운 사용자의 구매 결정을 돕는 서비스였습니다. 저희는 그중 백엔드 개발에 쓸 노트북을 고르는 문제에 집중했습니다. 팀원 모두 백엔드 개발자였고, 사용자에게 보이는 화면을 만드는 프론트엔드 기술에는 익숙하지 않았습니다.

프론트엔드 구현에는 AI의 도움을 적극적으로 받았습니다. 필요한 기능을 설명해 코드를 생성하고, 생성된 코드를 간단히 검토한 뒤 AI에 추가 코드 검토를 요청했습니다. 제가 익숙하지 않은 영역도 이런 방식으로 구현을 시작해 볼 수 있었습니다. 저희는 AI를 활용해 사용자 반응을 확인할 최소 기능 제품인 MVP를 만들고자 했습니다. 이 목적은 [프로젝트 기록](https://app.notion.com/p/AI-2-MVP-40cc62df7f5a80fe906fe22cb069bc31?source=copy_link)에도 남아 있습니다.

그런데 화면 구현에 사용할 React와 Thymeleaf 중 하나를 고르는 데는 여러 차례의 논의가 필요했습니다. AI가 코드를 작성해 주어도 우리 팀에 적절한 선택이 정해지지는 않았습니다. 두 기술이 어떻게 다른지, 저희가 어떤 이유로 선택했는지는 다음 절에서 살펴보겠습니다.

지금 필요한 기능은 무엇인지, 낯선 기술을 어디까지 알아봐야 하는지, 이후에 선택을 바꾸려면 어떤 작업이 필요한지 판단해야 했습니다. 팀원마다 경험과 기대가 달라 같은 기술의 장단점을 보고도 서로 다른 결론을 내렸습니다.

이 글에서는 초기 MVP에 Thymeleaf를 선택한 일, 이후 React로 전환한 일, 2주간의 구현 우선순위를 질문 게시판으로 바꾼 일을 돌아봅니다. 처음 기술을 선택하거나 팀의 구현 방향을 논의하는 개발자에게, 어디까지 조사하고 언제 선택을 다시 검토할지 고민했던 경험을 전하고 싶습니다.

## 초기 MVP의 Thymeleaf 선택

### 조사한 장단점을 우리 상황에 적용하기 어려웠습니다

처음 프론트엔드 기술을 논의할 때 후보는 React와 Thymeleaf였습니다. 두 기술 모두 사용자 화면을 만드는 데 활용할 수 있지만, 화면을 구성하고 데이터를 반영하는 방식에는 차이가 있습니다.

당시 MVP에 필요한 기능은 사용자의 용도와 조건을 묻는 온보딩 질문에 답변을 받으면, 그 답변을 바탕으로 제품 사양을 추천하고 해당 사양에 맞는 제품을 보여주는 것이었습니다. 질문 게시판처럼 사용자가 글을 작성해 남기는 기능은 요구사항에 포함돼 있지 않았습니다.

[Thymeleaf](https://www.thymeleaf.org/)는 서버에서 미리 작성한 화면 틀에 데이터를 채워 웹페이지 문서인 HTML을 만드는 도구입니다. [React](https://react.dev/learn)는 버튼이나 입력창 같은 화면 요소를 컴포넌트라는 단위로 구성하고, 데이터 변화에 맞춰 화면을 갱신하는 JavaScript 라이브러리입니다. 저희는 두 기술을 깊이 이해하지 못한 상태에서 비교를 시작했습니다. AI에 구현을 맡기더라도 어떤 방식을 택할지는 저희가 정해야 했습니다.

함께 작업하던 자리에서 먼저 이야기를 나눴지만 결론이 나지 않았습니다. 각자 장단점을 가볍게 조사한 뒤 다시 회의하기로 했습니다. 시간을 들여 조사하면 부족한 정보를 채우고 더 쉽게 선택할 수 있을 것이라고 생각했습니다.

두 번째 회의에서는 Thymeleaf를 사용하면 익숙한 Spring Boot 프로젝트 안에서 화면까지 함께 다룰 수 있다는 의견이 나왔습니다. [Spring Boot](https://spring.io/projects/spring-boot/)는 저희가 서버 애플리케이션을 만드는 데 사용하던 도구였습니다. 여기에 Thymeleaf를 연결하면 서버에서 화면에 필요한 HTML을 만들어 브라우저에 전달할 수 있습니다. 이런 방식을 서버 사이드 렌더링(SSR)이라고 합니다. 저희는 이 구성으로 현재 필요한 화면을 구현할 수 있다면, 초기에 배우고 관리할 범위를 줄이면서 MVP를 시작할 수 있을 것이라고 보았습니다.

React에 대해서는 새로 배워야 할 개념과 프론트엔드를 별도로 실행하고 배포하는 구성을 부담으로 생각했습니다. 동시에 앞으로 화면의 상호작용이 복잡해진다면 React가 적합하지 않겠느냐는 의견도 있었습니다. 여기서 상호작용은 사용자가 버튼을 누르거나 값을 입력했을 때 화면이 반응하는 것을 뜻합니다. 화면에 영향을 주는 입력값이나 선택값 등을 ‘상태’라고 하며, 이런 데이터를 유지하고 변경하는 일을 상태 관리라고 합니다.

여기에 AI가 구현을 맡아준다면 우리가 React를 깊이 배우는 부담을 크게 고려하지 않아도 되는 것 아니냐는 생각이 더해졌습니다. 당시 팀이 중요하게 보았던 기대와 우려를 정리하면 다음과 같습니다.

| 비교한 관점 | Thymeleaf에 대한 생각 | React에 대한 생각 |
| --- | --- | --- |
| 초기 구현 | 익숙한 백엔드 프로젝트 안에서 빠르게 시작할 수 있을 것 같다 | AI가 구현을 도와주면 익숙하지 않아도 시작할 수 있을 것 같다 |
| 학습과 관리 | 새롭게 알아야 할 범위와 관리 부담이 적을 것 같다 | 이해해야 할 개념과 실행·배포 구성이 늘어날 수 있다 |
| 화면 확장 | 지금 필요한 화면을 구현할 수 있는지 확인해야 한다 | 사용자 입력과 선택에 따라 여러 화면이 바뀌는 상황에 대응하기 좋을 것 같다 |

*표 1. 초기 회의에서 비교한 기대와 우려. 필자의 당시 경험을 바탕으로 정리했으며, 기술의 일반적인 우열을 평가한 표는 아닙니다.*

조사한 장단점은 늘었지만 그중 무엇이 현재 MVP에서 중요한지 판단하기는 여전히 어려웠습니다. 앞으로 필요할 수도 있는 복잡한 화면과 지금 빠르게 구현해야 하는 범위를 함께 이야기했습니다. 어느 쪽을 더 중요하게 볼지 정하지 못한 채 논의를 이어갔습니다.

### 외부 조언을 통해 현재 필요한 조건을 구분했습니다

결론이 나지 않자 우아한테크코스에서 프론트엔드 과정을 배우는 동료 교육생에게 고민을 전달했습니다. 우아한테크코스에서는 교육생을 ‘크루’라고 부릅니다.

조언을 구한 크루는 데이터의 생성·조회·수정·삭제를 뜻하는 CRUD가 중심인지, 사용자 입력에 따라 화면이 복잡하게 바뀌고 여러 상태를 관리해야 하는지에 따라 선택이 달라질 수 있다고 설명해 주었습니다. Thymeleaf로 MVP를 빠르게 만들고 이후 요구사항이 달라지면 React로 전환하는 방향도 선택지로 제시했습니다.

아래는 당시 받은 조언과 제 답변입니다. 지금 만들 MVP와 이후 기능 개선을 나누어 생각하게 된 대화였습니다.

![프론트엔드 크루가 요구사항에 따른 기술 선택과 추후 React 전환을 제안하고, 필자가 Thymeleaf로 시작하는 방향을 정리한 대화](테크니컬 라이팅/image/frontend-advice-conversation.png)

대화 속 성능에 관한 언급은 당시의 예상이며, 저희가 직접 비교해 얻은 결과는 아니었습니다. 이 조언을 통해 지금 필요한 화면과 향후 확장 가능성을 나누어 생각하게 됐습니다. 저도 초기에는 Thymeleaf로 시작하고 기능을 개선하는 단계에서 React 전환을 검토하는 방향으로 답변하며 선택 이유를 정리했습니다.

팀은 초기 MVP에 Thymeleaf를 사용하기로 했습니다. 당시에는 온보딩 답변을 바탕으로 사양을 추천하고 제품을 보여주는 흐름을 익숙한 백엔드 구성에서 빠르게 구현할 수 있을 것으로 보았습니다. 이후 필요한 기능이 달라지면 다시 판단하기로 했습니다. 향후 전환에는 화면 코드를 다시 작성하고 동작을 확인하는 비용이 남아 있었지만, 초기 선택에서 모든 확장 가능성까지 확정하려는 부담은 덜 수 있었습니다.

결정한 날의 회의는 제 기억으로 오전에 약 한 시간, 오후에 두 시간 정도 이어졌습니다. 그전의 논의까지 합치면 적어도 이틀에 걸쳐 이야기한 셈입니다. 결정을 마친 뒤에는 이 문제를 이렇게 오래 논의할 필요가 있었는지 돌아보게 됐습니다.

지금 돌아보면 비교의 전제부터 더 구체적으로 확인할 필요가 있었습니다. 당시에는 React를 쓰면 프론트엔드 서버를 하나 더 운영해야 한다고 생각했습니다. 하지만 React 앱은 배포용 HTML·CSS·JavaScript 파일을 만들어 제공하는 정적 파일 배포 방식으로도 운영할 수 있습니다. 별도의 애플리케이션 서버가 반드시 필요한 것은 아니므로, 실제 사용할 구성을 확인한 뒤 운영 부담을 비교했어야 했습니다. [React 공식 문서](https://react.dev/learn/creating-a-react-app), [Vite 배포 문서](https://vite.dev/guide/static-deploy.html)

AI가 코드를 작성해 준다는 기대도 구체적으로 살펴볼 필요가 있었습니다. 생성된 코드에 문제가 생기거나 요구사항이 바뀌었을 때, 팀이 어디까지 이해하고 수정해야 하는지 함께 질문했어야 했습니다.

장단점을 더 조사하는 것만으로는 부족했습니다. 어떤 조건을 기준으로 판단할지, 지금 어느 정도의 근거가 필요한지 함께 정해야 했습니다. 이 경험은 이후 회의 방식을 이야기하는 계기가 됐습니다.

## 논의의 깊이를 정하는 중요도와 비용

저희는 선택의 중요도와 변경 비용을 기준으로 논의의 깊이를 정하기로 했습니다. 여기서 논의의 깊이는 결정을 내리기 전에 무엇을 어디까지 조사하고 확인할지를 뜻합니다. 여기서 중요도는 선택이 사용자의 문제 해결과 현재 구현 목표에 미치는 영향의 크기를 뜻합니다. 변경 비용은 나중에 선택을 바꿀 때 다시 해야 하는 작업과 그에 드는 시간과 노력을 뜻합니다.

팀은 한 시간 동안 논의해도 결론이 나지 않으면 이 두 가지를 다시 살펴보기로 합의했습니다. 지금 더 깊이 검토해야 할 문제인지, 현재 확인한 근거로 진행하고 이후에 다시 검토할 수 있는 문제인지 판단하는 시간이었습니다. 추가 검토가 필요하다면 무엇을 더 알아봐야 하는지도 생각해 보기로 했습니다.

한 번의 회의는 두 시간을 넘기지 않는다는 원칙도 정했습니다. [팀의 회의·협업 원칙](https://app.notion.com/p/3-3ecc62df7f5a8055ba59dacd694cf28c?source=copy_link)에는 이 시간 제한과 함께, 잘 모르는 사안은 그 자리에서 결론을 내리지 않고 각자 알아본 뒤 다시 이야기한다는 내용이 있습니다.

즉, **한 시간은 논의의 방향과 깊이를 다시 판단하는 시점이고, 두 시간은 한 번의 회의를 마치는 기준**이었습니다. 조사와 후속 회의까지 포함해 모든 결정을 두 시간 안에 끝내자는 뜻은 아니었습니다. 이 구분을 흐름으로 표현하면 다음과 같습니다.

![한 시간 동안 결론이 나지 않으면 중요도와 변경 비용을 재판단하고, 현재 근거로 진행할지 추가 조사와 외부 조언을 거칠지 정하는 흐름](테크니컬 라이팅/image/meeting-review-flow.png)

중요한 의문이 남았다면 회의를 마친 뒤에도 조사하거나 외부에 조언을 구해 근거를 더 모을 수 있습니다. 회의가 끝났다는 이유로 검토까지 끝난 것으로 보지는 않기로 한 것입니다.

회의 시간과 함께 준비 방식도 정리했습니다. 팀의 작업과 협업 방식을 돌아본 [8월 24일 회고](https://app.notion.com/p/8-24-40cc62df7f5a806b897fc04f3922aba5?source=copy_link)에는 담당자가 안건과 사전 자료를 준비하고, 회의 진행과 기록을 맡도록 한 내용이 있습니다. 시간을 제한하더라도 무엇을 논의하고 어떤 근거를 바탕으로 판단할지 분명해야 했습니다.

경험을 돌아보면, 선택의 영향을 판단하려면 기술의 이름보다 어디에 얼마나 넓게 사용하는지 살펴봐야 했습니다. 일부 기능에 사용하는 도구와 여러 기능이 공통으로 사용하는 도구는 바꿀 때 영향을 받는 범위가 다를 수 있습니다. 현재 목표에 미치는 영향과 나중에 변경할 때 필요한 작업을 각각 확인해야 합니다.

변경 비용 외에도 선택한 방향을 실행하는 데 드는 시간과 노력인 투입 비용, 그동안 다른 기능을 구현하거나 가설을 검증할 기회를 놓치는 기회비용을 고려할 필요가 있었습니다. 이런 구분을 바탕으로 경험을 돌아보며 다음 질문을 정리했습니다.

| 판단할 내용 | 확인할 질문 |
| --- | --- |
| 선택의 중요도 | 이 결정이 사용자의 문제를 해결하고 현재 구현 목표를 달성하는 데 얼마나 큰 영향을 주는가 |
| 변경 비용 | 나중에 선택을 바꾸려면 어떤 코드와 화면, 데이터, 운영 절차를 다시 다뤄야 하는가 |
| 투입 비용 | 이 방향을 실행하는 데 얼마나 많은 시간과 노력이 필요한가 |
| 기회비용 | 이 방향에 시간을 쓰는 동안 어떤 기능 구현이나 검증, 학습을 미루거나 포기하게 되는가 |
| 남아 있는 불확실성 | 결정을 내리기 위해 아직 확인하지 못한 사실은 무엇이며, 어떻게 확인할 수 있는가 |

*표 2. 중요도와 비용을 구체화하는 질문. 필자가 프로젝트 경험을 돌아보며 정리한 것으로, 당시 회의에서 그대로 사용한 점검표는 아닙니다.*

이 기준으로 React 전환과 질문 게시판의 우선순위 결정을 차례로 돌아보겠습니다.

## 상태 관리와 확장을 고려한 React 전환

초기 MVP에서는 Thymeleaf를 선택했지만 이후 프론트엔드를 React로 전환했습니다. 이 결정의 배경과 비교한 대안은 [8월 24일 결정 문서](https://app.notion.com/p/React-vs-Thymeleaf-JS-40cc62df7f5a80bcb3c8fad4447424c1?source=copy_link)에 정리돼 있습니다.

초기 버전인 V0는 Spring Boot, Thymeleaf, 바닐라 JavaScript로 구현했습니다. 바닐라 JavaScript는 React 같은 화면 구성 라이브러리를 사용하지 않고 JavaScript로 직접 구현하는 방식을 뜻합니다. 저희는 Thymeleaf로 화면을 구성하고, 여러 화면에서 발생하는 사용자 입력과 그에 따른 화면 변화를 하나의 JavaScript 애플리케이션에서 관리했습니다.

V0에서는 온보딩 답변, 권장 사양, 제품 필터가 서로 영향을 주었습니다. 예를 들어 사양을 수정하거나 필터 조건을 바꾸면 관련된 표시와 제품 목록도 함께 갱신해야 했습니다.

이처럼 한 값이 바뀌었을 때 다른 값과 화면에 어떤 영향을 주는지 살펴봐야 했습니다. 기능이 늘어날수록 확인해야 하는 관계도 늘어날 수 있었습니다. 변경된 값에 맞춰 관련 화면이 빠짐없이 갱신되도록 코드를 작성하고 확인하는 부담을, 결정 문서에서는 상태와 화면의 ‘동기화 비용’으로 다뤘습니다.

이번 결정에는 다음 버전인 V1을 V0 코드를 재사용하지 않고 새로 구현한다는 전제도 있었습니다. 기존 화면을 그대로 유지하면서 일부 기능만 추가하는 상황과는 작업 범위가 달랐습니다. 따라서 React 선택의 이유를 읽을 때는 화면 관리에 대한 고민과 함께, 새 버전을 처음부터 구현하기로 했다는 조건도 고려해야 합니다.

두 선택에서 중요하게 본 조건을 나란히 놓으면 같은 팀이 다른 선택을 하게 된 배경이 드러납니다.

![초기에는 익숙한 백엔드 구성에서 빠르게 구현하기 위해 Thymeleaf를 선택했고, 이후 화면 상태 간 의존성과 V1 신규 구현 전제 아래 전체 React 전환을 선택한 비교](테크니컬 라이팅/image/frontend-decision-change.png)

React에서는 각 상태에서 어떤 화면을 보여줄지 코드로 정의하고, 상태가 바뀌면 그에 맞춰 화면이 갱신되도록 구성할 수 있습니다. 어떤 데이터를 상태로 관리하고 화면과 어떻게 연결할지는 개발자가 설계해야 합니다. [React 공식 문서](https://react.dev/learn/reacting-to-input-with-state)

저희는 이 방식을 활용해 답변, 권장 사양, 제품 필터를 중심으로 관련 화면을 구성하면 관리 부담을 줄일 수 있을 것으로 기대했습니다. 사양이나 제품 정보를 보여주는 카드, 선택지, 화면 상단과 하단의 공통 영역을 컴포넌트로 나누어 재사용하려는 목적도 있었습니다.

제품·가격 데이터를 API로 제공하게 될 가능성도 고려했습니다. 여기서 [API](https://developer.mozilla.org/en-US/docs/Glossary/API)는 화면에서 서버에 데이터를 요청하고 응답받을 때 사용하는 약속된 접점을 뜻합니다. 이런 방식으로 데이터를 가져온다면 요청 중일 때, 성공했을 때, 실패했을 때, 다시 요청할 때에 맞춰 화면을 보여줘야 합니다. 저희는 이 과정도 React의 상태 관리 방식으로 다룰 수 있다고 보았습니다. 제품·가격 데이터의 API 제공은 당시 문서에서 향후 가능성으로 다룬 조건이었습니다.

이번에는 React 사용 여부뿐 아니라 적용 범위도 비교했습니다. 모든 화면에 React를 사용하는 것과 사용자 입력에 따라 여러 표시가 함께 바뀌는 화면에만 사용하는 것은 필요한 작업이 달랐기 때문입니다. 이 비교에서 Thymeleaf를 사용한다는 것은 V1도 기존과 같은 기술 구성으로 새로 구현한다는 뜻입니다.

| 대안 | 기대한 이점 | 감수하거나 관리해야 할 비용 |
| --- | --- | --- |
| Thymeleaf와 바닐라 JavaScript로 V1 구현 | 익숙한 개발 환경을 활용하고 새롭게 도입할 기술과 설정을 줄일 수 있음 | 상태에 맞춘 화면 갱신, 클릭·입력에 따른 동작 연결, 공통 코드의 재사용을 직접 관리해야 함 |
| 모든 화면을 React로 구현 | 컴포넌트와 상태 관리 방식을 통일하고 공통 화면 요소를 재사용할 수 있음 | 안내 글처럼 상호작용이 적은 화면까지 React로 구현하고, 새로운 개발·배포 과정과 기능 검증을 다뤄야 함 |
| 복잡한 화면에만 React 적용 | 사용자 입력에 따라 자주 바뀌는 화면에 집중하고, 나머지는 기존 기술 구성을 활용할 수 있음 | Thymeleaf와 React가 각각 담당할 영역을 정하고 두 영역의 연결 방식을 관리해야 함 |

*표 3. React 전환 범위의 대안과 예상 비용. 출처: [8월 24일 결정 문서](https://app.notion.com/p/React-vs-Thymeleaf-JS-40cc62df7f5a80bcb3c8fad4447424c1?source=copy_link)를 요약.*

팀은 모든 프론트엔드 화면에 React를 사용하는 방향을 선택했습니다. 온보딩, 사양 확인과 수정, 제품 검색과 필터뿐 아니라 가이드와 여러 화면에서 공유하는 구성까지 같은 기술로 구현하기로 했습니다. 두 기술을 함께 사용할 때 생기는 담당 영역의 구분과 중복 구현을 줄이려는 판단이었습니다.

결정 문서에서는 서버와 화면의 역할도 나누었습니다. Spring Boot에는 API 제공과 데이터 처리, 서비스에서 발생한 일을 기록하고 저장하는 작업을 맡기기로 했습니다. React 기반 프론트엔드에는 데이터를 화면에 표시하고, 사용자 입력과 화면 상태, 페이지 이동을 처리하는 역할을 맡기기로 했습니다. 상태 변화가 적은 가이드 페이지에서는 React의 장점을 크게 활용하지 못할 수 있지만, 전체 프론트엔드의 개발 방식을 통일하는 쪽에 더 무게를 두었습니다.

감수해야 할 비용도 있었습니다. React와 개발에 필요한 라이브러리를 설치하고, 작성한 코드를 배포용 파일로 변환하고 묶는 [빌드 과정](https://vite.dev/guide/build.html)을 마련해야 한다고 보았습니다. 만들어진 JavaScript와 CSS 등의 파일을 사용자 브라우저가 내려받을 수 있도록 배포하는 과정도 필요했습니다.

기존에 제공하던 화면과 기능이 새 구현에서도 동작하는지 확인하는 작업도 남아 있었습니다. 화면에서 서버에 데이터를 요청할 주소와 주고받을 데이터의 항목·형식을 정해야 했습니다. 사용자 브라우저가 내려받는 JavaScript의 크기, 첫 화면이 표시되는 데 걸리는 시간, 검색 엔진에 페이지가 노출되는 방식의 변화도 확인할 항목으로 남겼습니다.

여기서 설명한 상태 관리와 재사용의 이점은 전환 당시의 기대입니다. React로 전환했다는 사실만으로 관리 부담이 실제로 줄었다고 말할 수는 없습니다. 문서에 남긴 비용 역시 예상한 작업과 확인할 항목이며, 실제 투입 시간이나 검증 결과와는 구분해야 합니다.

React 전환을 돌아보며, 기술 선택을 평가하려면 각 시점의 목표와 판단 조건을 함께 봐야 한다고 생각했습니다. 초기의 빠른 구현과 이후의 화면 관리 부담은 서로 다른 시점에 중요하게 본 조건이었습니다.

## 2주간의 구현 방향을 바꾼 재검토

### 제품 가치와 학습 목표가 함께 걸려 있었습니다

우아한테크코스의 교육 단계 중 하나인 레벨 4에서는 스프린트에 맞춰 프로젝트 작업을 진행했습니다. 스프린트는 일정한 기간 동안 목표를 정하고 작업하는 개발 주기입니다. 한 스프린트의 1주차에 저희는 앞으로 2주 동안 어떤 기능을 우선 구현할지 논의했습니다.

앞선 사례에서는 화면을 어떤 기술로 만들지 결정했습니다. 이번에는 무엇을 먼저 만들어 검증할지 정해야 했습니다. 교육 과정에서 진행하는 프로젝트였던 만큼, 저에게는 사용자의 문제를 해결하는 일과 새로운 백엔드 기술을 경험하는 일이 모두 중요했습니다.

저희는 백엔드 개발에 사용할 노트북을 고르기 어려워하는 사용자의 구매 결정을 서비스 기능으로 도울 수 있을지 확인하고 싶었습니다. 이를 위해 기존 추천 알고리즘을 개선하는 방향과 질문 게시판을 제공하는 방향을 논의했습니다. 추천 알고리즘은 사용자의 용도와 조건을 바탕으로 무엇을 추천할지 정하는 기준과 처리 방식입니다. 게시판을 선택한다고 기존 추천 기능을 없애자는 의미는 아니었습니다. 앞으로 개발 시간을 어디에 먼저 쓸지에 관한 논의였습니다.

추천 알고리즘을 개선하면 사용자에게 더 적절한 추천을 제공하고, 서비스만의 차별점을 만들 수 있다는 기대가 있었습니다. 다만 저는 추천이 나아졌는지 어떻게 확인할지, 정교한 알고리즘을 실제로 구현할 수 있을지에 확신이 없었습니다.

추천 기능에 대규모 언어 모델(LLM)을 활용한다면 모델 이용 비용도 고려해야 한다고 생각했습니다. LLM은 많은 텍스트를 학습해 문맥에 맞는 답변 등을 생성하는 AI 모델입니다. 이때 고려한 것은 서비스의 추천 기능 안에서 AI를 사용하는 방안이었습니다. [Google의 LLM 설명](https://developers.google.com/machine-learning/crash-course/llm/transformers)

저는 알고리즘 개선 과정에서 제가 원하는 백엔드 기술 경험을 얼마나 얻을 수 있을지도 확신하지 못했습니다. 이 걱정은 당시 제가 이해한 구현 방식과 원했던 경험에서 나온 것이며, 알고리즘 개선의 학습 가치 전반을 평가한 것은 아니었습니다.

질문 게시판은 사용자가 제품과 사용 목적에 관한 질문을 남기고, 다른 사용자가 답변하거나 기존 글을 찾아볼 수 있도록 하는 방향이었습니다. 저는 여러 온라인 카페에서 노트북 구매와 관련된 질문을 자주 보았습니다. 이를 보며 우리 서비스 안에서도 질문하고 정보를 얻을 수 있는 공간이 필요할 수 있다고 생각했습니다. 정보가 쌓이면 사용자가 다시 방문할 이유가 생길 것이라는 기대도 있었습니다.

학습 측면의 이유도 있었습니다. 당시 서비스에는 게시판처럼 사용자가 질문과 답변을 작성해 저장하고 다른 사람과 공유하는 기능이 없었습니다. 여기서 말하는 ‘쓰기 기능’은 이런 사용자 작성 내용을 서비스에 남기는 기능입니다. 저는 이를 개발하면서 새로운 백엔드 개발 경험을 얻고 싶었습니다. 게시판에 대한 제 판단에는 사용자에게 필요한 기능이라는 생각과 제가 경험하고 싶은 기술이라는 목표가 함께 들어 있었습니다.

게시판에도 한계가 있었습니다. 사용자는 이미 온라인 카페나 유튜브에서 비슷한 정보를 얻을 수 있었습니다. 구매 질문이 많이 보인다는 관찰만으로 우리 서비스에 게시판을 만들면 사용자가 찾아올 것이라고 결론 내릴 수는 없었습니다. 기존 서비스와 어떤 차이를 만들 수 있을지도 생각해야 했습니다.

다음 표는 제가 이해한 두 방향의 기대와 우려입니다.

| 선택지 | 기대한 가치 | 제가 판단하기 어려웠던 점 |
| --- | --- | --- |
| 추천 알고리즘 개선 | 더 적절한 추천을 제공해 서비스의 차별점을 만들 가능성 | 개선 효과를 어떻게 확인할지, 구현 가능성과 비용은 어떨지 |
| 질문 게시판 | 구매 질문과 정보를 쌓고, 사용자 작성 내용을 저장·조회하는 기능을 개발하는 경험 | 기존 커뮤니티와 어떤 차이를 만들지, 실제 이용으로 이어질지 |

*표 4. 두 기능에 대해 필자가 당시의 논의와 경험을 돌아보며 정리한 기대와 우려. 팀원 모두의 평가가 같았다는 의미는 아닙니다.*

### 회의를 마친 뒤에도 의문은 남았습니다

논의를 이어가면서 두 팀원의 의견은 추천 알고리즘 개선으로 모였습니다. 저는 충분히 설득되지 않았지만 회의를 계속 늘릴 수는 없다고 생각했습니다. 제 기억으로 약 한 시간 반 정도 이야기한 뒤, 알고리즘 개선 방향으로 회의를 마무리했습니다.

회의가 끝나도 고민은 남았습니다. 게시판의 필요성과 그 과정에서 얻을 수 있는 기술 경험을 쉽게 내려놓기 어려웠습니다. 한편으로는 제 의견 때문에 같은 논의를 계속 반복하는 상황도 만들고 싶지 않았습니다.

이때 앞서 합의했던 중요도와 비용을 다시 생각했습니다. 앞으로 2주 동안 한 방향에 시간을 쓰면 그 과정에서 얻는 경험과 함께, 미뤄지는 다른 기능의 검증도 생깁니다. 사용자에게 어떤 도움을 줄 수 있을지와 제가 어떤 개발 경험을 얻고 싶은지를 더 확인할 필요가 있다고 생각했습니다.

저는 팀원들에게 게시판을 쉽게 포기하기 어려운 이유를 설명했습니다. 사용자의 구매 질문을 보며 필요성을 느꼈고, 현재 서비스에 없는 쓰기 기능을 개발하면서 얻고 싶은 경험도 있다고 이야기했습니다. 그리고 프로젝트와 학습 방향에 관해 조언을 구할 수 있는 우아한테크코스 코치에게 이 고민을 함께 전달해 보자고 제안했습니다.

팀원들은 이 선택의 중요성과 비용을 고려해 제안을 받아들였습니다. 이후 시간을 잡고 함께 코치와 이야기를 나눴습니다. 같은 자리에서 논의를 계속 이어가기보다, 판단에 도움이 될 다른 관점을 구하는 행동으로 옮길 수 있었습니다.

### 코칭 후 팀 전체의 우선순위가 바뀌었습니다

코치와의 상담인 코칭에서는 어떤 기술 경험을 하고 싶은지도 선택에 반영해 보자는 취지의 조언을 받았습니다. 이후 팀은 질문 게시판을 먼저 구현하는 방향으로 우선순위를 바꿨습니다. 개인의 의문에서 시작한 재검토가 팀이 함께 구현 방향을 바꾸는 결정으로 이어졌습니다.

여기서 설명한 우려와 학습 목표는 제 관점입니다. 팀이 질문 게시판을 선택했다는 것이 모든 팀원이 같은 이유로 판단했다는 뜻은 아닙니다.

이때 정한 것은 무엇을 먼저 구현할지였습니다. 게시판이 실제로 사용자의 구매 결정에 도움이 되는지, 기존 커뮤니티 대신 우리 서비스를 이용할 이유가 되는지는 별도로 검증해야 했습니다.

회의 종료부터 우선순위 변경까지를 순서대로 정리하면 다음과 같습니다.

AI는 정한 방향을 실행하는 데 필요한 인력을 생각할 때도 영향을 주었습니다. 여기서는 게시판 코드를 작성하는 데 AI의 도움을 받는 것을 뜻합니다. 저는 AI의 도움을 받으면 여러 팀원이 게시판 개발에 함께 투입될 필요는 없다고 판단했습니다. 초기 프론트엔드 회의에서는 익숙하지 않은 기술도 AI로 구현할 수 있을지를 생각했다면, 이번에는 선택한 기능을 어느 정도의 인력으로 구현할 수 있을지 판단하는 데 AI 활용을 고려했습니다.

저는 이 과정을 거치며 회의를 끝내는 일과 중요한 의문을 해소하는 일을 구분하게 됐습니다. 제 경우에는 우려를 구체적으로 설명하고 코칭을 제안하는 것이 다음 행동이었습니다. 팀원들이 그 제안을 받아들였기 때문에 재검토도 가능했습니다. [이후 회고](https://app.notion.com/p/Sprint-1-4-40cc62df7f5a80dface9d79f6f28dff0?source=copy_link)에도 결론이 나지 않을 때 조사를 하거나 코칭으로 전환했다는 내용이 남아 있습니다.

## 세 결정에서 얻은 기준과 남은 한계

초기 MVP에 Thymeleaf를 선택할 때는 익숙한 구성으로 필요한 화면을 빠르게 만들 수 있는지가 중요했습니다. React로 전환할 때는 서로 영향을 주는 화면 상태를 관리하는 부담과 V1을 새로 구현한다는 전제를 살폈습니다. 질문 게시판을 먼저 구현하기로 할 때는 앞으로 2주 동안 무엇을 만들고 검증할지, 그 과정에서 어떤 기술 경험을 얻고 싶은지를 함께 고민했습니다.

세 결정을 돌아보면 각 상황에서 필요한 근거가 달랐습니다. 모든 선택을 같은 깊이로 조사하려고 하면 지금 필요하지 않은 가능성까지 검토 범위가 계속 넓어질 수 있습니다. 그렇다고 회의 시간을 정해 두는 것만으로 결정에 필요한 근거가 갖춰지지는 않았습니다. 현재 목표에 얼마나 큰 영향을 주는 선택인지, 실행하거나 나중에 바꾸려면 어떤 작업이 필요한지, 아직 확인하지 못한 사실은 무엇인지 설명할 수 있어야 했습니다.

조언을 구할 때는 무엇을 판단하기 어려운지 먼저 정리해야 했습니다. 팀의 의견과 다른 생각을 제시할 때도 의문이 생긴 이유와 다음에 확인할 일을 함께 설명하는 것이 필요했습니다. 질문 게시판 사례에서는 이 설명과 코칭 제안을 팀원들이 받아들여 재검토를 이어갈 수 있었습니다.

이 경험에서 확인한 것은 선택의 이유를 구체화하고, 중요한 의문을 팀과 다시 검토하는 과정입니다. 질문 게시판 사례에서는 실제로 팀의 구현 우선순위도 바뀌었습니다. 다만 이런 방식으로 회의 시간이 전반적으로 줄었는지, 완성된 기능이 사용자의 노트북 구매 결정에 더 도움이 됐는지는 이 글에서 다룬 사례만으로 판단하기 어렵습니다.

추가 검토에도 시간과 노력이 필요합니다. 외부에 조언을 구하려면 일정을 맞추고 프로젝트 상황과 고민을 설명해야 합니다. 자료를 조사하고 판단의 근거를 기록하는 작업도 필요합니다. 따라서 검토를 더 하기로 했다면 어떤 의문을 해소하려는지, 조사나 조언을 통해 무엇을 확인할지 먼저 정해야 합니다.

반대로 검토를 줄이기로 할 때도 이유를 공유해야 합니다. 어떤 선택이 현재 목표에 미치는 영향이 작다는 판단과, 나중에 쉽게 바꿀 수 있다는 판단은 별개입니다. 다른 팀원이 아직 논의에 나오지 않은 위험을 생각하고 있을 수도 있습니다. 영향이 작다고 본 이유와 변경할 때 필요한 작업을 함께 살펴봐야 어디까지 확인하고 진행할지 합의할 수 있습니다. 중요한 의문을 다시 검토할 때처럼, 검토를 멈출 때도 판단의 근거가 필요했습니다.

코드 작성을 돕는 AI의 역할도 이런 기준으로 돌아보게 됐습니다. AI로 구현할 수 있다는 기대는 어떤 기능을 시도할지, 구현에 어느 정도의 인력이 필요할지 판단할 때 고려할 조건이었습니다. 생성된 코드를 팀이 이해하고 수정할 수 있는지, 배포하고 운영하는 데 어떤 작업이 필요한지도 살펴봐야 합니다. 만든 기능이 사용자의 문제를 해결하는지는 실제 이용 결과로 확인해야 합니다. 코드가 만들어졌다는 사실만으로 그 기능을 선택한 이유나 사용자에게 주는 가치까지 확인되는 것은 아닙니다.

## 다음 기술 선택에서 팀이 함께 답할 질문

세 결정을 돌아보며, 기술을 고르거나 먼저 구현할 기능을 정할 때 팀이 함께 확인할 질문을 정리했습니다. 회의를 준비하거나 논의가 길어질 때 무엇을 더 확인할지 정하는 데 활용할 수 있습니다. 프로젝트의 목적과 팀의 상황에 맞게 바꾸어 적용해 보시기 바랍니다.

1. 지금 해결하려는 사용자의 문제는 무엇입니까? 학습도 프로젝트의 목표라면, 이번 작업에서 어떤 기술 경험을 얻고 싶습니까?
2. 지금 구현해야 할 기능과 그에 필요한 조건을, 앞으로 필요할 것으로 예상하는 기능이나 조건과 구분했습니까?
3. 이 선택을 구현하는 데 필요한 시간과 노력은 어느 정도이며, 나중에 바꾸려면 어떤 작업을 다시 해야 합니까? 그동안 미뤄지는 다른 기능 구현이나 검증은 무엇입니까?
4. 논의가 반복되는 이유는 무엇입니까? 아직 확인하지 못한 사실은 무엇이며, 조사나 외부 조언으로 어떻게 확인할 수 있습니까?
5. 회의가 끝나도 결정에 영향을 줄 수 있는 의문이 남아 있습니까? 남아 있다면 무엇을 더 확인하고 언제 다시 논의하겠습니까?
6. 필요한 기능이나 관리 부담, 사용자 반응에 어떤 변화가 생기면 지금의 선택을 다시 검토하겠습니까?

처음에는 기술 하나를 고르기 위해 어디까지 알아봐야 하는지가 막막했습니다. 이제는 어떤 정보가 부족하고, 그 정보를 더 확인하는 일이 이번 결정에 왜 중요한지부터 생각합니다. AI가 코드를 작성해 주는 상황에서도 현재의 선택 이유를 설명하고, 남은 의문을 기록하며, 조건이 달라졌을 때 다시 판단하는 일은 저희의 몫이었습니다.
